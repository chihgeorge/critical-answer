## Problem Statement

critical-answer's question bank has three parallel question kinds: `text`, `multipleChoice`, `image`. The founder, who is also the sole question-writer for this side project, wants question content (and a new answer-reveal explanation) to be able to use text, an uploaded image, or a YouTube video interchangeably, instead of image being its own bolted-on kind.

## Demand Evidence

Real but diffuse: pushed four times, the founder could not name a specific blocked question, but confirmed under direct pressure that it has actually happened — "確實發生過：有題目因為格式限制而妥協/放棄" (yes, it happened: a question was compromised or abandoned because of format limits). Not hypothetical, but a single, un-nameable instance — the cross-model second opinion flagged this as thin evidence for a full schema rewrite (see below).

## Status Quo

When blocked, the founder switches to a text description or verbally supplements at answer-reveal time. Cost is real but non-fatal — "效果打折" (the effect is diminished), not broken.

## Target User & Narrowest Wedge

The founder themselves (question-writer/host) is the sole and central user — confirmed directly, consistent with this project's pattern across two prior features (DM voice narration, multi-segment narration), where the founder was equally honest that both were his own taste rather than player-demanded.

## Constraints

- Solo side project, not yet public (per 2026-09-23 durable decision: stays private until a 1.0 milestone, monetization undecided).
- Existing architecture, shipped one day before this session (v0.6.0.0, `image-question-type` design doc): `BankStore` Durable Object, Cloudflare R2 upload via `/api/bank/image`, `lib/question-bank.ts` kind-switcher UI in `app/bank-editor/page.tsx`.
- `check:bundle` CI gate: only server-only code may import parsed `BANK` data; client components import types/pure logic only from `lib/question-bank.ts`.

2. Status-quo cost is real but non-fatal — **agreed**.
3. The founder is the sole and central user — **agreed**.
4. Premise kept on that basis.

## Approaches Considered

### Approach A: Minimal — two fields on existing kinds (not chosen)
Add `content`/`explanation?` fields typed to a small union, retire `image` as a standalone kind by making it one media type within `content`. Reuses existing R2 upload path directly.
- Effort: S-M, Risk: Low
- Rejected because it doesn't generalize to future media types (audio, PDF) without another schema pass — the founder's own stated reason for wanting B.

### Approach B: Ideal architecture — generic `MediaContent` union (chosen)
Define one `MediaContent = { kind: "text" | "image" | "youtube"; value: string }` type used everywhere content can appear: question, explanation, and (future) individual multiple-choice options. `image` retires as a standalone question kind entirely — it becomes a `MediaContent` variant. **Per-kind `value` shape (decided, R1-3):** `text` → the plain string, no markdown; `image` → the R2 object key (not a full URL — mirrors the existing `image`-kind decision to store the key and let `publicQuestion()` prepend the base URL, so switching the serving domain later needs no bank migration), **still validated against the same `UUID_RE` shape check `lib/question-bank.ts` already enforces on `imageKey` today (R2-2)** — that check exists specifically to close off a hand-crafted key pointing outside the bucket (see the existing comment at `lib/question-bank.ts:61-65`), and a generic `value: string` must not silently drop it; `youtube` → the extracted video ID (not the raw pasted URL) — extracted once at save time so render never re-parses.
- Effort: M-L **plus a one-time backward-read conversion for existing `image`-kind data (see Dependencies, R1-4)** — this is real work the original estimate didn't name, not new scope.
- Risk: Medium (touches every render point: bank editor, `/play`, `/screen`, host page)
- Reuses: existing R2 upload endpoint and `BankStore` Durable Object; the `image` kind's upload/validation logic becomes the `MediaContent`-kind image path instead of a separate question kind.
- **Extends cleanly (revised, R2-3)**: a future media kind (audio, PDF) is one new union member and one new `case` at each existing render/edit site (bank editor, `/play`, `/screen`, host page) — TypeScript's exhaustiveness checking on the `kind` switch means the compiler forces every site to be touched, so this is *not* zero-consumer-touching. What's actually saved versus adding a whole new top-level question kind (the `image`-kind precedent) is the type-level diff: one union member instead of a new discriminated variant of `Question` itself, which would additionally need its own parse/validate function, its own entry in every place that currently switches on `Question["kind"]`, and its own bank-editor "add question" option. The consumer-touching cost is comparable either way; the schema-shape cost is not.
- **`<MediaPicker>` type-switch behavior (decided, R1-6):** switching a slot's media type discards the prior value immediately, no draft-preservation across kinds — matches v1 simplicity elsewhere in this codebase (e.g. the bank editor doesn't preserve a question's old answer when its kind changes today). If the slot being switched away from is non-empty (an uploaded image, a filled-in YouTube URL), the picker shows a native `confirm()` before discarding — same cheap pattern already used for other destructive UI actions in this codebase, no custom modal needed.

### Approach C: Creative/lateral — single string field with embedded syntax (not chosen)
No discriminated union; one string per content slot, parsed at render time for embed syntax (`![img](url)`, `{{youtube:ID}}`).
- Effort: M, Risk: Medium-High (hand-rolled parser edge cases, low error tolerance)
- Rejected without much debate — smallest schema footprint, but trades a typed model for a fragile custom parser for no clear benefit at this project's scale.

## Recommended Approach

Approach B, chosen by the founder after the cross-model challenge on premise 4. The founder explicitly weighed the second opinion's cheaper field-patch (Approach A, which is materially the same shape as the prototype it proposed) against the generalized model, and chose B for a stated, specific reason (avoiding repeated schema changes as new media types are anticipated) — not simply defaulting to the more ambitious option.

## Success Criteria

An owner can, for any question (currently `text` or `multipleChoice` kind), pick text/image/YouTube for the question content, and independently pick text/image/YouTube for an optional answer-reveal explanation. The image path reuses the existing R2 upload flow end to end (upload, validation, `/play`/`/screen` display, broken-image fallback). **The YouTube path gets an analogous failure story for what a plain iframe can actually detect (revised, R2-4)**: an inline edit-time error when a pasted URL doesn't match a recognized YouTube URL pattern (mirrors the existing upload-time validation) — this case IS reliably detectable with the chosen "regex only, no API calls" approach. A deleted/private video is a different case: a bare `<iframe>` to a dead/private YouTube video still returns 200 and renders YouTube's own in-page "video unavailable" message, with no cross-origin load-failure event the parent page can observe — the stated "no API calls" approach cannot detect this at render time. **Decided**: v1 does not attempt to detect a deleted/private video after the fact; only the edit-time URL-pattern check is implemented. Detecting a since-deleted video would require the YouTube IFrame Player API (a script include, `onError` via postMessage) — deferred, and only worth adding if it's actually hit in practice. The standalone `image` question kind no longer exists as a separate kind **in the type system** going forward; existing on-disk data in that shape is converted lazily, not left to coexist indefinitely as a schema variant the app must keep authoring new questions into (see Dependencies for exactly what "converted" means).

That precedent is read-time-only (it patches the in-memory object; it does not itself trigger a write), so to be honest about what "no longer left to coexist indefinitely" means here: the converted shape is what every reader sees immediately, but the *on-disk* bank JSON keeps the old `image`-kind bytes until the next time `BankStore.putBank()` writes the bank wholesale (which happens on any host edit — `putBank()` already saves the entire bank on every PUT, per the R2-cleanup design's own analysis of that path). No big-bang migration script; no permanent dual-shape support in the type system read by the app. This conversion (the read-time shim, not a separate rewrite pass) is real, scoped work and is folded into Approach B's effort estimate above.

### R1-1 — consistency

**Problem**

> Success Criteria states the standalone `image` question kind "no longer exists as a separate kind in the schema going forward" — a definitive, committed behavior — while Open Questions and Dependencies leave undecided whether existing `image`-kind questions already live in the bank (shipped one day before this session, per Constraints) get migrated to `MediaContent` or coexist in both shapes during a transition. A schema that drops the `image` kind cannot simultaneously leave open whether old data in that kind is converted or supported; one of these has to give. Framing this as an Open Question does not resolve the contradiction with the stated Success Criterion.

**Remedy**

> Either soften the Success Criterion to acknowledge a transition period where both shapes may coexist, or commit now to a migration approach (even a placeholder like "one-time script, TBD in /plan-eng-review") so the criterion and the dependency don't contradict each other.

### R1-2 — completeness

**Problem**

> Success Criteria explicitly calls for the image path to reuse "the existing R2 upload flow end to end (upload, validation, /play/screen display, broken-image fallback)," giving the image variant a defined failure behavior. No equivalent behavior is specified for the youtube variant: what happens on an unparseable URL, a deleted/private video, or a regex match that yields an invalid ID (the design commits to "regex-extracted video ID in an iframe, no API calls," which cannot detect these at write time).

**Remedy**

> Define a fallback for invalid/broken YouTube content analogous to the image fallback (e.g., inline error state at edit time, and/or a broken-embed placeholder at render time), or explicitly note it's deferred to /plan-eng-review.

### R1-3 — clarity

**Problem**

> The `MediaContent` type is given as `{ kind: "text" | "image" | "youtube"; value: string }` with a single generic `value: string` across all three kinds, but the document never specifies what that string holds per kind — e.g. whether the image variant's value is an R2 object key or a full URL, whether the youtube variant's value is the raw URL, an extracted video ID, or an embed URL, and whether the text variant supports any formatting (plain string vs. markdown). This is a design decision the next engineering review needs already made, not inferred.

**Remedy**

> Specify the concrete shape of `value` for each kind (or explicitly leave it as a named open question for /plan-eng-review rather than an implicit gap in the type definition).

### R1-4 — feasibility

**Problem**

> Dependencies states the migration strategy for existing `image`-kind questions "blocks a clean cutover more than it blocks a first build," acknowledging real migration work exists — but Approach B's stated effort (M-L) and risk (Medium, "touches every render point") is scoped only around reuse of the existing R2/BankStore path and rendering surfaces. Migration/dual-shape-compatibility work is not reflected in that estimate, so the stated effort likely understates what's needed for the schema change to be safe to ship against live data.

**Remedy**

> Either fold a migration/compatibility-shim line item into Approach B's effort estimate, or explicitly flag that the effort estimate assumes migration is out of scope for the first build.

### R1-5 — scope

**Problem**

> The chosen Approach B (full generic `MediaContent` union used "everywhere content can appear": question, explanation, and future multiple-choice options) is justified mainly by anticipated future media types (audio, PDF) beyond the two-field patch Approach A would have covered. The document's own Assignment admits this headroom might be "purely hypothetical" and that the answer "doesn't change the chosen approach" — meaning the higher-effort, higher-risk (Medium, touches every render point) approach is locked in before the evidence-gathering step (the Assignment) that would test whether the extensibility is concretely needed. This is a YAGNI risk the document surfaces but does not actually resolve before committing engineering effort.

**Remedy**

> Either make the Assignment's outcome load-bearing (i.e., the union's exact membership/extensibility effort is scaled by what the founder actually writes down), or explicitly state as a decision — not just a risk to note — that the founder accepts speculative scope now regardless of the Assignment's outcome.

### R1-6 — completeness

**Problem**

> Approach B introduces a shared `<MediaPicker>` component letting an owner pick text/image/YouTube per content slot, but no behavior is specified for what happens when an owner switches a slot's media type after content already exists (e.g. an already-uploaded image, switching to YouTube) — whether the prior value is discarded silently, preserved in case they switch back, or requires confirmation before data loss.

**Remedy**

> Specify the switch-type behavior for the `<MediaPicker>` (discard with/without confirmation, or preserve per-kind drafts), or add it explicitly to Open Questions if deferred to /plan-eng-review or /design-consultation.

## Architecture Decisions (/plan-eng-review)

**D1 — `content` replaces the question's `text` prompt, not decoration alongside it.** The existing `image` kind kept a fixed `text` prompt plus `imageKey` as a supplement. Under D1, a question's `content: MediaContent` IS the question — `content.kind === "image"` shows only the image, no separate text line. This matches the actual use case named this session (a video-only question: "watch this MV, guess the song") and is a real field reduction (the old `text`+`imageKey` pair collapses into one `content` field), not just a rename.

**D2 — a new `ANSWER_REVEALED` broadcast, sent to `/play` and `/screen`, carrying the correct answer text plus optional `explanation: MediaContent`.** Today the answer is host-only (`HOST_ANSWER`, sent via `sendTo`, never `broadcast` — see `lib/protocol.ts:105` and `lib/room/dungeon-room.ts:350-353`). Outside Voice flagged this as a potential competitive-integrity regression (a team could see today's answer, then get dealt the same question again later via `game-state.ts`'s reshuffle-on-exhaustion or the boss ring's fixed cycle). **Resolved (D3) after user input**: this is a shared-screen, in-person party game — everyone in the room already sees `/screen` together, so restricting the broadcast's audience doesn't actually protect anything in this social context. The real fix is D4 below, not narrowing who receives `ANSWER_REVEALED`.

**D4 — `game-state.ts`'s `deal()` must skip questions whose answer has already been revealed when reshuffling a room's pool, falling back to allowing reuse only once every question in the pool has been revealed.** Verified: `deal()` (`lib/game-state.ts:185-201`) currently reshuffles a room's full question pool back in once exhausted (`used[roomIndex] = []`), and the boss pool is a fixed ring — both allow a question (and now, under D2, its already-broadcast answer) to repeat. This needs a new "revealed" set (distinct from `used`, which only tracks per-team currently-held questions) that `deal()`'s reshuffle branch filters against, with the pre-D2 no-repeat-protection behavior as the exhaustion fallback (better to repeat a question once every other one is spent than to end the game early).

### Implementation-level fixes (verified against source, no user decision needed — these are correctness requirements, not design tradeoffs)

- **`imageKeysOf` (`lib/question-bank.ts:193-199`) must be rewritten to scan `content.value`/`explanation.value` on both surviving kinds (`text`, `multipleChoice`), not filtered by a top-level `q.kind === "image"` that will no longer exist.** Verified this feeds `BankStore.putBank()`'s (`lib/bank-store.ts:102-121`) orphan-diff, which fires real R2 deletes (`worker/index.ts:58`, `deleteOrphanedImages`). Left as originally scoped, the very first save after this schema ships would see every previously-tracked image key as "orphaned" (new-kind's `imageKeysOf` returns empty) and delete every live image referenced through the new fields — a mechanically-certain data-loss bug, not a corner case. This must be part of the same change that removes `image` as a top-level kind, not a follow-up.
- **`handleHostJudge` (`lib/room/dungeon-room.ts:741-756`) must capture the just-judged question's answer and `explanation` from `prev` (via `currentQuestion()`) BEFORE `this.game = game` reassigns to post-judgment state** — mirroring the existing `monster` capture on the same line, which already has to work around this exact ordering trap for narration. Reading `this.game` after the reassignment (as `broadcastState()`/`sendAnswer()` already do for `HOST_ANSWER`) gives the *next* question's answer, not the one just judged. `ANSWER_REVEALED` must not inherit this trap.
- **YouTube ID format validation must be enforced inside `parseBank`'s question parser** (the same trust boundary `UUID_RE` is checked at, `lib/question-bank.ts:65,72`, reached by any authenticated `PUT /api/bank` — see `lib/bank-api.ts`), not only in the bank-editor UI at "save time." Build one `parseMediaContent(value, kind)` helper used for both `content` and `explanation` at both call sites, so kind-specific validation (UUID shape for `image`, ID shape for `youtube`) can't drift between the two fields via copy-paste (Outside Voice finding).
- **`PublicQuestion.text` (`lib/protocol.ts:36-44`) is currently required and unconditionally read** at `app/room/[code]/screen/page.tsx:148`, `app/room/[code]/play/page.tsx`, and `app/room/[code]/host/page.tsx:302`. Under D1 this field is replaced by `content`, meaning these three render sites need a `content.kind` switch, not just a new optional branch — removing a field every consumer currently assumes exists, not only adding one.
- **`parseQuestions`'s shared `text` non-empty check (`lib/question-bank.ts:95`)** runs before per-kind parsing for every kind today; under D1 this shared gate needs to move into per-kind `content` validation, not stay as a blanket pre-check.
- **R1-6's "same cheap pattern already used for other destructive UI actions" claim is factually wrong** — `grep -rn "confirm(" app/ components/` returns zero results; there is no existing `confirm()` anywhere in this codebase, including the bank-editor's own question-delete button. The `<MediaPicker>` discard-confirmation is new UI pattern work, not reuse. (Does not change the decision, corrects the stated rationale.)
- Test files needing rewrite as part of this change (not a separate follow-up): `lib/question-bank.test.ts`'s `imageKeysOf` tests (currently assert `q.kind === "image"` behavior directly), plus new coverage for `parseMediaContent`, the `deal()` revealed-question exclusion, and the `handleHostJudge` capture-before-reassignment ordering.
