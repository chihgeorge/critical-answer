# Design: 魔王分成多個階段（surprise phases）

Generated by /office-hours on 2026-10-28
Branch: boss-phases-design
Repo: chihgeorge/critical-answer
Status: APPROVED
Mode: Builder

## Problem Statement
The host is preparing a boss music bank for an event. It has two modes: guess the singer and song title, and guess which work a theme song comes from. Today the boss fight is one HP bar over one question list, so both modes are mixed in a single ring and nothing marks the switch. The host wants the boss fight split into phases, each with its own question set, so the fight has a shape.

## What Makes This Cool
- **The second phase is a surprise.** Phase 1 looks like an ordinary boss: no phase label and no hint that more is coming. When its HP runs out, the big screen shows 「還沒結束！第二階段」. The boss comes back with a full new HP bar, a new colour and a new rule, such as 「聽前奏，說出這首是哪部作品的主題曲」.
- **Each phase changes how you play, not just how much HP is left.** That matches the common guidance on boss design: a phase should change the mechanics, not only the numbers.

## Constraints
- **Surprise:** players never learn how many phases there are, or that another one follows. Nothing on `/screen` or `/play`, and nothing in any broadcast message, may reveal the phase count or a future phase's name, rule or HP. Only the host page knows. This is a trust boundary like the answer one: future-phase data goes only to host connections.
  - **What may be broadcast:** the current phase's ordinal (`bossPhase`: 1, 2, …). It names only a phase already reached, never the total, so the screen can print 「第二階段」 and pick the hue.
- **Old banks:** a bank without phases plays exactly as today, as one phase.
- **Format:** the bank format changes, so `BANK_FORMAT` in `lib/bank-store.ts` goes up by 1. An older deployment then refuses to save over a phased bank instead of dropping the phases (v0.15.2.4 TODO note).
- **Reuse:** extend existing parts rather than add new systems, specifically:
  - the boss ring (`nextBossQuestionId`, `rotateBoss`)
  - the answer-reveal pause (`HOST_NEXT`)
  - the boss-enter narration
  - the host's boss pick (v0.15.3.0)

## Premises (agreed)
1. **Phases:** each phase is a named group of boss questions with its own HP bar. The boss is defeated only when the last phase's bar is empty. An old bank reads as a single phase and behaves as today.
2. **Phase change:**
   - The big screen shows a title card with the phase name and that phase's rule, a narration line plays, and the boss changes colour.
   - The host presses 「下一題」 to continue.
   - The player screens never show a phase count, not even after the first reveal (decided in the sketch round).
3. **A phase runs out of questions:**
   - If every question in a phase has been revealed and its HP is not empty, the fight moves to the next phase automatically.
   - The phase's remaining HP pays no reward.
   - The last phase has no next phase, so it repeats its own questions (today's rule).
4. **Rewards:**
   - Every hit pays the boss's hit reward as today.
   - The kill bonus (4d20) is paid only for the final blow of the last phase.
5. **Host pick:**
   - 「指定首領房下一題」 lists only the current phase's questions.
   - A phase change clears any pick.
6. **Bank and editor:**
   - The bank format holds several phases, and `BANK_FORMAT` goes up by 1.
   - The bank editor's 首領 tab can add and remove phases, and set each phase's name, rule text and HP.

## Approaches Considered
- **A: one boss with phases (chosen).** The boss keeps one monster and one hit reward and gains a list of phases. Each phase has a name, rule, HP and questions. The smallest change, and it fits this event.
- **B: a full phase system.** Each phase sets its own monster, music, rewards and a layered HP bar. Rejected: far more surface (screen, map, narration, scoring, editor) than the event needs.
- **C: a boss chain (bosses as a list).** Recommended in the session but not chosen; the user preferred to keep one boss that changes form.

## Recommended Approach (A)
**Bank shape.**
- `boss` keeps `monster`, `hitReward` and kill dice.
- `maxHp` and `questions` move into `boss.phases: { name, rule, maxHp, questions }[]`.
- A bank without `phases` is parsed as one phase `{ name: "", rule: "", maxHp, questions }`.
- `parseBank` requires every phase to have `maxHp ≥ 1` and at least one question.
- ~~The editor warns when a phase has fewer questions than its HP plus a few.~~ Dropped by the eng review (D6): no phase shows a question-count warning, and the old boss-tab warning goes too.

**Question ids.** Question ids are unique across the whole bank, all pools and all boss phases together. `parseBank` rejects a duplicate and the editor never creates one. So a question belongs to exactly one phase, and 「revealed」 is unambiguous.

**Game state (`lib/game-state.ts`).**
- `BossState` gains `phases: { maxHp, questionIds }[]` and `phaseIndex`.
- `hp`/`maxHp` describe the current phase.
- The boss ring (`nextBossQuestionId`, `rotateBoss`) walks only the current phase's ids.
- **Hit:** when a hit empties a phase that is not the last, the phase advances:
  - `phaseIndex + 1`
  - `hp` set to the new phase's `maxHp`
  - the current question becomes the new phase's first unrevealed question
  - the queued pick is cleared
  - the outcome is a new `boss-phase` result (a hit plus the phase change) instead of a kill.
- **Out of questions:**
  - **When:** the check runs at every boss rotation, after a hit or a rotating miss or flee. If the current phase has no unrevealed question left and it is not the last phase, the phase advances exactly as above.
  - **Reward:** none for the HP the phase still had.
  - **Outcome:** the same `boss-phase` outcome, with `reason: "exhausted"` (versus `"cleared"` for an emptied bar). It carries the hit's reward when it follows a hit, and none after a miss.
  - **Show:** it gets the same phase card, narration, hue change and 下一題 pause as a cleared phase.
- **Kill:** only the last phase's final blow kills the boss and rolls the kill bonus.

> **Superseded by the Eng Review (D1, D7, D9):** the game state does not change at the triggering answer; it only sets `boss.phasePending`, and `enterNextBossPhase` runs when the card opens. There is no room-side `pendingPhase` and no view masking, except that STATE's `question` is null while the card shows. Read the Eng Review section below before this subsection and the next two.

**Ordering of the pauses (both reasons).**
1. **The answer** (only when the triggering answer was correct): the room shows the normal answer reveal for the question just answered.
2. **The phase card:** 下一題 closes the reveal and the room shows the phase card. After a miss that exhausts the phase there is no answer to reveal, so the card shows right away.
3. **The new phase:** 下一題 closes the card and the new phase's first question appears.

The game state changes once, at the triggering answer: `phaseIndex`, `hp`, the current question and the cleared pick. The two pauses only hold back what the screens show. The new question is never on screen before the card closes, because the reveal and then the card replace the question area, as the answer reveal does today.

**What the broadcast view shows during the pauses.** The room keeps a server-side `pendingPhase` (the phase being entered) from the triggering answer until the card closes, and builds `SpectatorView` from it:
- **During the answer reveal:** the old phase. `bossPhase` is the old ordinal, `bossHp` is 0 (or the old phase's remaining HP for an exhausted phase), and `bossMaxHp` is the old phase's maximum. No future-phase data is in that STATE; the only hint is a 0-HP bar without a game over (see below).
- **When the card opens:** `pendingPhase` moves into `phaseReveal`, and the view switches to the new phase (new `bossPhase`, full `bossHp`/`bossMaxHp`).
- **When the card closes:** `phaseReveal` is cleared and play continues normally.
- **Restore:** `pendingPhase` is saved with the room. The answer reveal is memory-only, so a restore during the reveal step resumes at the phase card; a restore during the card shows the card again.
- **Question withheld:** while `pendingPhase` is set, STATE's `question` is null, so the new phase's question never reaches a client before the card closes.
- **Narration and cue at the triggering answer:** they are the ordinary hit ones (or none after a miss). The `boss-phase` narration and its sound cue fire only when the card opens.
- **0 HP on a clearing hit:** the reveal shows `bossHp` 0 with the game still playing. There is no kill cue, no `bossKilledBy` and no GAME_OVER. The suspense ("did we win?") is intended: the card then answers it.

**Saved rooms.** A room saved before this change stores a `BossState` with no `phases` or `phaseIndex`. On restore it is read as one phase `{ maxHp, questionIds }` with `phaseIndex: 0`, so a live room survives the Worker deploy. A persistence test loads such an old snapshot.

**Room and wire (`lib/room/dungeon-room.ts`, `lib/protocol.ts`).**
- The phase-change title card reuses the reveal pause: STATE carries a `phaseReveal: { name, rule }` while it shows. Only the phase being entered is included, never a count.
- The host presses 下一題 (`HOST_NEXT`), as after a correct answer.
- `SpectatorView` keeps `bossHp`/`bossMaxHp` for the current phase only, and adds `bossPhase` (the current ordinal). The total and any future phase's data are never broadcast.
- The host page learns the phase list (names, HP, which one is current) through a host-only message (`HOST_PICKS` or a sibling), never STATE.
- Host pick options for `"boss"` become the current phase's questions.

**Big screen (`app/room/[code]/screen/page.tsx`).**
- The title card overlays the question area with 「還沒結束！第二階段」 (or 第三, …), the phase name, its rule and the new HP bar.
- The boss sprite's hue shifts by a fixed step per phase. There is no per-phase hue field.
- No phase label is shown during a phase.

**Narration (`lib/narration/events.ts`, scripted + LLM).**
- A new `boss-phase` event plays a line like 「小黑龍的鱗片轉成赤紅，戰鬥進入第二階段！」.
- The LLM prompt gets the phase name and rule only.

**Editor (`app/bank-editor/page.tsx`).**
- The 首領 tab lists phases. Each has a name, rule text, HP and its own question list, plus 新增階段 and 刪除階段.
- The existing per-boss fields (monster, hit reward) stay at the top.

Wireframe (layout only; final look comes from /plan-design-review in the game's pixel style): `docs/designs/img/boss-phases-sketch.png`. A copy was sent in the session. Left panel: phase 1 looks like a normal boss. Right panel: the phase card 「還沒結束！第二階段 / 主題曲之謎 / 聽前奏，說出這首是哪部作品的主題曲」 with a fresh 2-HP bar.

## Open Questions
- **Hue step:** which hue step per phase still reads as the same monster? Decide with real sprites in /plan-design-review.
- **Live map:** does the boss room on the live map show anything at a phase change (a flash), or stay unchanged to keep the surprise?
- **Phone wording:** after a phase change, do the phones show the new rule text, or only the big screen?
- **Late joiners:** a team entering the boss room mid-phase-2 faces phase 2. Does the boss-enter narration mention the phase? Default: no, to keep the count hidden.

## Success Criteria
- An event host can build a two-phase music boss in the editor, save it, and run it.
- Phase 1 shows no hint of phase 2. Emptying it shows the surprise card with the new rule, and phase 2 asks only its own questions.
- A phase that runs out of unrevealed questions moves on by itself. The game never stalls or repeats a phase-1 question in phase 2.
- An old single-boss bank plays exactly as before. All existing boss tests pass unchanged, or change only where the new shape requires it.
- Neither the broadcast STATE nor any `/screen` or `/play` payload contains the phase count or a future phase's data. Only the current ordinal `bossPhase` appears. A test asserts this, alongside the existing answer-leak checks and `npm run check:bundle`.

## Distribution Plan
The existing deployment pipeline covers this: Vercel for the web app, plus a Cloudflare Worker deploy for the room logic. Bump `BANK_FORMAT` in the same release.

**Deploy order (changed by the Eng Review, D8): the Worker and the web app ship together.** The new Worker's GET returns the phased shape, which the old editor cannot read, so a gap between the two deploys breaks the editor (not rooms). Rollback: rolling the Worker back mid-event discards every live room whose saved bank has phases (the old parseBank refuses it; fail closed, "game reset"). The original text follows for history.

~~**Deploy order: the Worker first, then the web app.**~~ The bank is parsed and stored by the Worker (`BankStoreDO`, `lib/bank-store.ts`), so the Worker must understand phases before any editor can send one.
- **Web app first instead:** the new editor would send a phased bank to the old Worker. The old `parseBank` rejects it, because it has no `boss.questions`, so the save fails with a 400 and nothing is stored or lost.
- **Worker first:** the old editor keeps working. It sends single-boss banks, which the new Worker reads as one phase.

### R3-1 — consistency (blocking)

**Problem**

> The new section only rebuilds `SpectatorView` from `pendingPhase`.
