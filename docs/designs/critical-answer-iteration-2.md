# CEO Plan: Critical Answer Iteration 2 (Atmosphere First)

## Why this iteration exists

Iteration-1 real playtest (2026-09-18): mechanics passed (turn order, boss last-hit, pacing). Players said they cannot judge whether the game is fun without narrative immersion, visuals, and UI. Fact check: the app never displays question text today. The host page shows only ids like "r2-q1" and the host reads from a paper sheet. Phones are read-only status views.

Hypothesis under test: **atmosphere is the product**. Success is measured by a second real playtest, compared against iteration 1.

## Approach chosen: C (atmosphere-first + LLM narration with scripted fallback)

Rejected: A (scripted narration only, no LLM) because the user wants the AI DM differentiator in this iteration. Rejected: B (full design-doc iteration 2: LLM + narrative layer + live map + editor) because it repeats the "five subsystems before validation" shape flagged in the iteration-1 eng review.

## Baseline scope (Approach C)

1. Question bank inside the app (JSON). Big screen shows question text, difficulty, monster. Replaces the paper sheet. Existing ids in `lib/fixtures.ts` stay the join key.
2. `NarrationEvent`: typed events derived from `AnswerOutcome` in `lib/game-state.ts` (correct, incorrect-retry, incorrect-flee, boss-hit, boss-kill, game-over). This is the seam every downstream consumer reads.
3. `NarrationProvider` interface with two implementations:
   - Scripted provider: hand-written line library, keyed by event type, random pick, always available.
   - LLM provider: Claude API, called server-side (API key never reaches the browser), one call per event, hard timeout, falls back to scripted on timeout, error, empty, malformed, or refusal.
4. Big-screen dungeon-themed UI: question, monster, boss HP bar, current narration line, turn indicator, simple animations.
5. Player phone view shows the same narration line plus own team status.
6. Narration observability: every event logs id, provider used, latency, fallback reason.

## Spec corrections (from adversarial review, verified against code)

Facts, not decisions:

- `AnswerOutcome` has 4 variants: `correct-room-advance`, `correct-boss-hit` (with a `bossKilled` flag), `incorrect-flee`, `incorrect-retry`. It is NOT six event types. `boss-kill` is a flag on `correct-boss-hit`. `game-over` is not an outcome; it is a `GamePhase` change. The `NarrationEvent` mapper must be a pure function `toNarrationEvent(prevGame, nextGame, outcome)` in `lib/`, unit-tested, and must add the context the outcome lacks (team name, room index, monster, question text, difficulty, boss HP).
- `handleHostJudge` in `party/index.ts` currently discards `outcome` (`const { game } = answerQuestion(...)`). Wiring the outcome through is part of this work.
- `answerQuestion` is synchronous and `broadcastState()` fires right after it. An LLM call must never block the STATE broadcast. Sequence: STATE first, then a separate `NARRATION` message when ready, ordered by monotonic `eventId`.
- `lib/protocol.ts` has no message for narration, epilogue or question payload. Add `NARRATION` and `EPILOGUE` to `ServerMessage`. The room stores `lastNarration` and `epilogue` so REJOIN and late joiners see the current line.
- `GameState` keeps no event log. The room must accumulate `events[]` in memory. `broadcastState()` re-sends `GAME_OVER` on every call after the game finishes (onClose, REJOIN), so the epilogue must be generated exactly once, guarded by a flag, or it will re-call the LLM.
- `hostConnId` is the first connection; only it can send `HOST_JUDGE`. The "big screen" is the host page. There is no separate spectator role.
- The 20 existing questions (15 room, 5 boss) live in `docs/question-bank-2026-taiwan.md` with no monster names. The bank schema needs a monster or theme field and a boss identity.
- TODOS.md "content moderation before LLM prompt" was blocked on LLM integration. This plan removes that block, so it becomes in scope for the LLM provider (team names are user-supplied and only strip `<>&"'`).
- TODOS.md does not yet contain E1, E3-E6, the editor or the wrangler bypass detail. They are added as part of finishing this review.

Both host-token gated, recorded in the D12 transcript |

After a wrong answer the host picks: retry (same question), flee-same-room (next question in the room, same monster), flee-switch-room (jump to another room and monster). Both flee kinds lower difficulty by 1. Defaults pending user confirmation: switch-room goes to the next room this team has not cleared and the abandoned room stays available; if `extraRooms` runs out the team is let into the boss room; starting question within a room is staggered by team order so later teams do not hear answers first |

## Diagrams

System architecture (see the review transcript, Section 1). State and flow deltas:

```
  Wrong answer, host chooses:
    retry            ─▶ same question, same room
    flee-same-room   ─▶ next question in this room, same monster, difficulty -1
    flee-switch-room ─▶ next uncleared room, new monster, difficulty -1
  Correct answer:
    room cleared ─▶ score += difficulty
      score >= 15 ─▶ boss gate opens
      all rooms cleared and score < 15 ─▶ append room from extraRooms
      extraRooms empty ─▶ boss gate opens anyway
```

```
  Narration timeline for one judged answer
  HOST_JUDGE ─▶ STATE(broadcast, immediate)
             ─▶ NARRATION{eventId=n, provider:scripted}      immediate
             ─▶ LLM call (<= 3 s)
                  ├─ ok, event n still latest, no host edit ─▶ NARRATION{eventId=n, provider:llm}
                  └─ otherwise ─▶ dropped (stale, timeout, error, or host edit)
```
