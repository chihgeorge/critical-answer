## Problem Statement

v1.0 定義（前一份設計）已經把「題庫編輯介面」列為必做項目，但只設計了單一題型（文字題+文字答案）。使用者這次想討論兩件事：(1) 題庫編輯器要支援不同類型的題目，不只文字；(2) 現有的單向 AI 旁白（`lib/narration/llm.ts`）要升級成玩家真的能互動的「AI Dungeon Master」模式，讓答題過程感覺像在跑桌遊，而不是填測驗。兩者 scope 都大，需要分階段。

## What Makes This Cool

「哇」時刻不是 AI 的新奇感本身，而是**共桌的劇場感與後果感**——玩家做的選擇真的變成了故事的一部分，首領登場時還會被提起。這比單純的旁白文字生動，也比「純測驗」更接近使用者真正想要的跑團體驗。

## Constraints

- 現有核心玩法（出題 → 作答 → host 判分）已驗證好玩、必須保留，不可被取代。
- 沒有玩家內容審核機制（TODOS.md 開放項目），任何新增的玩家輸入面都會放大 prompt injection 風險。
- `lib/room/dungeon-room.ts` 已有狀態持久化、旁白事件、LLM fallback 路徑；Durable Object 的輸出閘道只在 `onMessage` 語意下安全（fire-and-forget 寫入需在後續 send/broadcast 前），`onAlarm()` 等其他路徑需顯式 await。
- 題庫驗證規則（每房最少題數、首領題數、難度下限、答案不可外洩進題目文字）目前只活在 `lib/question-bank.test.ts`，`parseBank` 沒有強制執行——任何面向使用者的編輯器都必須把這些規則搬進正式 validator。
- 題庫編輯器的權限/儲存架構已在前一份設計定案（owner key、KV 或 D1），本文件不重議。
- 分支狀態必須與既有房間持久化/生命週期機制相容：房間閒置 2 小時會關閉所有連線休眠（遊戲狀態仍在），24 小時會被整個遺忘。分支選擇如果在持久化完成前房間休眠或重啟，不能遺失或卡在中間狀態——必須走 `persist()`/`restore()` 既有的持久化路徑，不能是獨立於它的新狀態。
- Durable Object 的輸出閘道規則對這個新寫入路徑同樣適用：分支選擇的持久化寫入若發生在 `onMessage` 語意下（玩家/host 點按觸發），可沿用「fire-and-forget 寫入 + 後續 broadcast」的既有模式；若發生在 `onAlarm()` 或其他非 `onMessage` 路徑，必須顯式 `await`，不能假設輸出閘道保護。

## Premises

1. 題庫編輯器沿用既有的權限/儲存架構決策（owner key、KV 或 D1），不重新討論。— 同意
2. 題型要可擴充：先設計 schema，再實作選擇題、圖片題等具體類型。— 同意
3. AI DM 分支選項是疊加在現有核心玩法上，不取代、不改變現有出題/判分流程。— 同意
4. DM 分支的「結果」必須由程式碼確定性判定，LLM 只負責敘事，不負責決定勝負/傷害/戰利品。— 同意

## Cross-Model Perspective

Codex（`codex exec`，read-only，`model_reasoning_effort=high`）的獨立冷讀：

1. **最酷的版本**：Campaign replay map——每次分支選擇在大螢幕上留下可見路徑；圖片題變成路徑上的「文物」；首領登場時回顧隊伍實際做過的選擇；結尾用 QR 碼放「前情提要」回顧。規則引擎記錄每個節點，LLM 只負責照事實寫「預告片」文案。
2. **最能反映興奮點的一句話**：「玩家答題要感覺像被跑團 DM 帶著玩，而不是在填測驗」——代表使用者要的是共桌的劇場感與後果感，不是 AI 新奇感或內容管理工具本身。接受固定選項反而印證了這點：要「有掌控感的錯覺」，不犧牲公平、host 可判分的遊戲性。
3. **可重用的既有做法**：題庫用 JSON Schema 2020-12 + Ajv 做 `kind` 判別式聯合型別驗證（`text` / `multipleChoice` / `image`），拿到約 50%（匯入匯出格式檢查、欄位錯誤訊息、安全加新題型）；剩下一半要自己做——TypeScript type registry（每種題型的編輯器/公開投影/host 判分畫面/grading adapter）、圖片上傳儲存、權限版本紀錄、把驗證規則從測試搬進正式 domain validator。
4. **一個週末的建議**：先做 AI DM，因為 `DungeonRoom` 已有狀態持久化、旁白事件、LLM fallback 路徑，在「答對→進下一房」後有乾淨的接縫可插；題庫編輯器要一次跨過儲存選型、owner 驗證、版本衝突、匯入匯出、驗證邏輯、多種畫面呈現，才會變成桌上看得到的東西。最小可展示版本：清完第一房後暫停，給隊伍一個雙按鈕選擇，把結果持久化成地圖/戰利品狀態，餵給旁白並在首領登場時重提，不動分數/判分邏輯。

搜尋佐證（本次 office-hours 的即時搜尋）：AI DM 社群公認的架構原則是「AI 只負責敘事，規則引擎另外算」（RoleForge 模式）——LLM 生成的「隨機數」不是真隨機，不能拿來當判定依據。這印證了前提 4。

## Approaches Considered

### Approach A: DM 先，題庫編輯器後
- 先做單一分支的 DM 插曲（清完第一房後暫停，雙按鈕選擇，結果進地圖/戰利品狀態，餵旁白，首領登場回提），再做題型 schema，題庫編輯器 UI 最後。
- Effort: S-M（human: ~1-2 天 / CC: ~2-3 小時，**估時偏樂觀**——未包含 Open Questions 全部 5 項（決策主體、按鈕語意、判定邏輯、LLM 降級、DO 寫入順序驗證）定案後可能追加的範圍，`/plan-eng-review` 應重新估時）　Risk: 低
- Pros: 最少新基礎設施；重用 `DungeonRoom` 既有接縫；一週內可產生「我們的決定真的改變了冒險」的可展示時刻。
- Cons: 題庫編輯器（v1.0 已定案必做項目）往後延；朋友玩測前題庫還是得手動改 JSON。
- Reuses: `lib/room/dungeon-room.ts` 的持久化與旁白事件、`lib/narration/llm.ts` 的 prompt 架構。

### Approach B: 題庫編輯器先，DM 後
- 先把 JSON Schema + Ajv 的可擴充架構、owner key、儲存（KV/D1）、validator 從測試搬進正式發布，再做 DM。
- Effort: L（human: ~3-5 天 / CC: ~4-6 小時）　Risk: 高（機率大、可玩成果最慢見到）
- Pros: 長期架構紮實；之後 DM 需要新題型時不用回頭改題庫。
- Cons: 跨儲存選型、owner 驗證、版本衝突、匯入匯出、驗證邏輯、多種畫面呈現，一次要扛的面很大；風險最高。

### Approach C: DM 最小分支先上，題庫編輯器等下次玩測回饋
- 只做最小版 DM 分支（不做地圖、不做回顧），題庫編輯器維持手動改 JSON，等下次真人玩測回饋再決定要不要推進 Campaign replay map 或題庫編輯器。
- Effort: S（human: ~0.5-1 天 / CC: ~1 小時）　Risk: 最低
- Pros: 投資最小、最保守。
- Cons: 這季可能玩不到題庫編輯器。

## Recommended Approach

**Approach A（DM 先）**——使用者選定。用最少新基礎設施製造「哇，我們的決定真的改變了冒險」時刻，且完全不動現有判分邏輯；題庫可擴充 schema 與編輯器 UI 接續在後。

## Open Questions

- **兩個按鈕分別代表什麼？**（道德選擇？資源取捨？純敘事風味，無機制差異？）這是比「結果判定邏輯」更基礎的問題，兩者都留給 `/plan-eng-review`，但按鈕語意必須先定，判定邏輯才有依附的對象。**按鈕選項文字預設為固定預寫（host/開發者定稿），不接受玩家自由輸入**——若維持這個預設，Constraints 裡「沒有玩家內容審核機制」那條警語對本功能不適用（不放大 prompt injection 面），因為玩家只是從固定選項點選；`/plan-eng-review` 若考慮讓選項文字動態生成，須重新評估這條約束是否解除。
- **誰來按這個選擇？** 房間是多人共用（最多 4 隊），「雙按鈕選擇」若是全房共用一個選擇，決策主體要定義：全員一致才算數？多數決？還是由 host 代表整場按？這是多人房間互動的核心邏輯，`/plan-eng-review` 必答項，不能隱含在「玩家能看到選擇」這句話裡。
- 分支選項的「結果」判定邏輯（機率表？固定劇本？）尚未設計，留給 `/plan-eng-review`。
- **首領回提選擇的敘事，LLM 掛掉時怎麼降級？** 現有的 LLM fallback 路徑是給「一般旁白」設計的；「回提本場已發生的選擇」需要引用具體事實，純文字模板能不能達到同樣效果，還是直接跳過這段。**暫定預設：LLM 不可用時直接跳過回提，不硬套模板**（避免模板文字聽起來生硬或跟實際選擇不搭），除非 `/plan-eng-review` 有更好方案。
- Campaign replay map（大螢幕路徑回顧、首領回提）是否要在第一版就做，還是等玩測回饋——Codex 建議先做最小版本，不做地圖。
- 題型 schema（JSON Schema 2020-12 + Ajv 判別式聯合型別）的實際欄位定義留給 `/plan-eng-review`。
- 題庫驗證規則從測試搬進正式 validator 的時間點——建議跟題庫編輯器一起做，不要在 DM 分支這波動它。

## Success Criteria

- 清完第一房後，玩家能看到一個雙按鈕選擇，選擇被持久化，且在首領登場時旁白會提起這個選擇。
- 完全不改變現有答題/判分的資料流與測試。
- DM 分支的結果由程式碼決定，不是 LLM 產生；有一個可執行的檢查（unit test）驗證這一點。
- 朋友玩測時能看到「決定真的影響了故事」的反應。

## Next Steps

1. `/plan-eng-review`：設計分支選項的資料模型（存在 `dungeon-room.ts` 的 persisted state 裡哪個欄位）、結果判定邏輯、旁白 prompt 怎麼吃「已確定的選擇事實」。
2. 實作「清完第一房 → 雙按鈕選擇 → 持久化 → 首領登場回提」的最小垂直切片；持久化寫入需確認符合 Constraints 裡的輸出閘道規則（`onMessage` 觸發可 fire-and-forget，其他路徑需顯式 `await`）。
3. 寫一個 unit test 斷言分支結果永遠來自程式碼而非 LLM 輸出（例如 mock LLM 回傳任意文字，斷言遊戲狀態不受影響）。
4. 朋友玩測收集回饋，再決定要不要做 Campaign replay map（大螢幕路徑視覺化）。
5. 題型 schema（JSON Schema + Ajv）與題庫編輯器 UI，排在 DM 分支驗證過後。

## What I noticed about how you think

- 你一開始把題庫編輯器的討論收斂成「架構本身沒問題，想討論的是不同類型的題目編輯器」——沒有重新打開已經定案的權限/儲存決策，只挑真正還沒想清楚的部分繼續深挖，這種範圍界定的精準度不是每個人都有。
- 對 DM 模式，你自己先講了「疊加在現有玩法上」，選擇了風險較低的方向，而不是被「自由對話 DM」這個比較炫的版本吸引走——你在乎的是遊戲仍然公平、host 仍然可判分，這個判斷比多數人先想到的還務實。
- 兩次追問（先做選擇題還是圖片題、DM 想讓玩家做什麼）你都選了「先講架構，不確定具體」——這不是迴避決定，是正確地把「還沒想清楚」和「架構要先扛得住任何答案」分開處理。
