## Problem Statement

critical-answer is a self-hosted party trivia game the founder built and hosts for their own friend gatherings. The question bank currently supports `text` and `multipleChoice` kinds; `image` was explicitly deferred out of the `question-bank-editor` PR to keep that PR's scope down. The founder is now considering whether this could grow past a hobby project, and wants to decide what to build next.

## Demand Evidence

The founder or friends have actually played the game. After a session, someone proactively asked "when can we play again" and/or wanted to bring other friends — real behavioral demand, not just polite interest.

## Status Quo

The group currently uses Kahoot/Jackbox-style tools. Under pushback, three real pain points surfaced (not one):
1. **Paywalls/limits** — the founder confirmed, with specific evidence, that they were actually blocked by a Kahoot paywall or question-count limit during a past session (not hypothetical).
2. **Fiddly setup / high barrier to start** — getting a session actually running is friction-heavy.
3. **No narrative immersion** — generic Q&A, no story or character investment, unlike critical-answer's existing DM-narrated dungeon framing.

## Target User & Narrowest Wedge

The founder themselves — they are the host/organizer of every gathering. What they care about most: "everyone has fun / good vibe," not efficiency or looking impressive. Any feature should be scored against "does this make the host better at reading and driving the room," not "does this make the tool more capable."

## Approaches Considered

### Approach A: Full image question type + R2 upload (chosen)
Add `image` kind to the bank editor, Cloudflare R2 bucket binding, upload form with validation, `/play` and host-screen image display.
- Effort: L (human: ~4-5 days / CC: ~3-4 hours — revised up slightly after the outside-voice routing/abstraction/cleanup findings below)
- Risk: Medium — upload validation, R2 cleanup on question delete/replace, broken-image fallback
- Reuses: `BankStore` Durable Object, the `multipleChoice` kind-switcher UI pattern from `app/bank-editor/page.tsx`
- **Upload transport (decided)**: through the Worker, not a client-obtained presigned URL. The bank editor already routes every mutation through the owner-key-gated `/api/bank` endpoint on the Worker; a second, separate presigned-URL flow would duplicate auth and add a second trust boundary for no real benefit at this project's scale (personal question images, not bulk media). Images upload via a new `/api/bank/image` Worker endpoint (raw binary POST body, owner-key-gated), which writes to R2 and returns the object key. `MAX_BANK_BODY_BYTES` governs the bank JSON PUT only and does not apply to this endpoint — it gets its own independent size cap (see Success Criteria). Like the existing PUT handler, the 5 MB cap is enforced against actual bytes read while streaming the upload, never the client-declared `Content-Length` header — same attacker-controlled-header lesson the existing bank PUT handler already had to apply (`lib/bank-api.ts`).
- **Routing (outside-voice correction, verified against code)**: `worker/index.ts` already routes the entire `/api/bank` and `/api/bank/*` prefix into `handleBankApi()`, which dispatches on HTTP method only (GET/PUT/OPTIONS) and 405s anything else — it does NOT look at the path. `/api/bank/image` as originally described would be silently swallowed and rejected by the existing handler, not routed to new code. Fix: `handleBankApi` (or a new sibling function it delegates to) must dispatch on `pathname` within the `/api/bank/*` prefix before falling through to the existing GET/PUT logic, so `/api/bank/image` reaches new code and `/api/bank` keeps its current behavior unchanged.
- **Platform-abstraction discipline (outside-voice correction)**: `lib/bank-api.ts`'s header comment is explicit that this layer is "platform-agnostic on purpose... none of the logic here knows Cloudflare exists" — `worker/index.ts` injects the real Durable Object RPC calls as `BankApiDeps`. The new image-upload handler must follow the same seam: a pure, testable function taking an injected `putImage(bytes, contentType): Promise<{ key: string }>` dependency, with the actual R2 binding call living only in `worker/index.ts` — never reaching into Cloudflare APIs directly from the shared handler code.
- **Serving strategy (decided)**: R2 bucket configured for public read access via its `r2.dev` subdomain, not signed URLs. `/play` and `/screen` are unauthenticated pages — a signed-URL scheme would need an expiry/re-signing policy just to keep old, resting games playable, which is unwarranted complexity for non-sensitive question images. Public bucket path means the URL is stable and never expires. **`r2.dev` production-use risk (accepted, /plan-eng-review)**: Cloudflare's own docs mark `r2.dev` as test-only, throttled at "hundreds of requests/second." Verified via [Cloudflare's public-buckets docs](https://developers.cloudflare.com/r2/buckets/public-buckets/) and [R2 platform limits](https://developers.cloudflare.com/r2/platform/limits). Accepted as a real but currently-negligible risk: the project has no owned custom domain yet (runs on `workers.dev`/`vercel.app`), and the actual usage pattern (a handful of teams, 1-10 images per party) is orders of magnitude below the throttle threshold. Upgrade path: attach a custom domain to the R2 bucket once either a domain is purchased or real traffic approaches the threshold — no data migration needed, only a URL-base change.
- **Schema storage (decided)**: the question record stores only the R2 object key, not the full URL. `publicQuestion()` (server-side, `lib/question-bank.ts`) prepends the R2 public base URL when building the client-facing `PublicQuestion`, mirroring the existing `PARTY_HOST` pattern (`lib/party-host.ts`) — the base is an environment concern, never baked into stored bank data, so switching the serving domain later (e.g. to a custom domain) needs no bank migration.
- **Orphan-on-partial-upload (accepted risk)**: if the upload step (`/api/bank/image`) succeeds but the follow-up `/api/bank` PUT that references the new key never completes (navigation away, network drop, PUT rejected), the R2 object is never cleaned up by any of the three named triggers below. Accepted as a low-priority gap for v1 — it costs a small amount of unused R2 storage, never a functional bug (an unreferenced object is never served to a player). A reference-counting or periodic-sweep fix is deferred until it's actually worth building.
- **Image display fit (decided)**: `/play` and `/screen` render images with CSS `max-width`/`max-height` and `object-fit: contain` (aspect ratio preserved, no cropping or server-side resizing) — standard, no new infrastructure.

### Approach B: Host-flow friction audit + tightening
Audit the actual host loop (create room → teams join → start → judge/advance per turn) for click count and stall points; fix the worst offenders.
- Effort: S-M (human: ~1-2 days / CC: ~1 hour)
- Risk: Low — touches existing, tested code paths, no new subsystem
- Second opinion's recommended pick — directly serves the confirmed "setup friction" pain point and the core "good vibe" driver

### Approach C: Minimal image support — external URL only, no R2
Add `image` kind but skip upload entirely; host pastes an image URL, game renders it directly.
- Effort: XS (human: ~half day / CC: ~30 min)
- Risk: Low-medium — URL validation/hotlinking, no data-ownership burden
- Cheapest way to validate whether image questions actually improve "vibe" before investing in R2 infrastructure

## Recommended Approach

Approach A, chosen by the founder after weighing all three. Rationale: image questions serve a pain point the founder confirmed as real (lack of narrative immersion) and the architecture was already scoped in a prior design doc — the founder judged the full version worth building directly rather than validating cheaply first, accepting the R2 infrastructure cost as one-time investment rather than deferred risk.

**Noted but deferred**: Approach B (host-flow friction) remains the most direct lever on the *other* confirmed pain point (setup friction) and on the core value driver ("good vibe" hinges on the host not fumbling mid-party). This is not addressed by shipping A, and is worth a future office-hours session or TODOS.md item once A ships.

**Cost re-check (outside-voice finding)**: tracing the plan against the actual routing/handler code (`worker/index.ts`, `lib/bank-api.ts`) surfaced that Approach A's real engineering surface is larger than first costed — a routing fix (the existing `/api/bank/*` catch-all would otherwise swallow the new endpoint), a platform-abstraction seam to keep R2 access out of the shared handler code, and a before/after reference-diff mechanism for cleanup (none of which Approach C, the paste-a-URL option, would need at all). None of this changes the recommendation — the founder chose A twice, once already knowing the second opinion's cheaper alternative — but it's now named explicitly rather than hidden inside an "L, 2-3 hours CC" estimate that didn't account for it.

## Open Questions

- Is the live host loop (clicks per judge/advance cycle) actually smooth, or untested? Nobody has measured this — Approach B's premise is unverified, not disproven.
- Exact R2 cleanup implementation (reference-counting vs. delete-on-edit vs. periodic sweep) — the trigger events are decided (see Success Criteria); the mechanism is a `/plan-eng-review` implementation detail.

## Success Criteria

An owner can upload an image via the bank editor, mark a question as `image` kind, and have it render correctly on both `/play` (team phones) and the host's big screen (`/screen`).

- **R2 cleanup mechanism (revised, outside-voice correction)**: the original three named triggers (question deleted, image reference changed, kind switched away) implicitly assumed per-question old-vs-new diffing exists somewhere in the save path — it doesn't. `BankStore.putBank()` validates and stores the entire new bank wholesale on every PUT; there is no per-question change detection today, and building one is a nontrivial addition to the one path every bank mutation already goes through. Simpler, equivalent mechanism that needs no diffing: after any successful `putBank()`, compute the set of image keys referenced anywhere in the *new* bank (a single pass over all questions, which the save path already has in memory), compare it against the set referenced by the *previous* versioned bank (read before the write, already fetched for the version-conflict check), and delete any R2 object whose key is in the old set but not the new one. This single "before/after reference-set diff" naturally covers all three original cases (delete, replace, kind-switch) without special-casing any of them. Room close/expiry is still NOT a trigger — images belong to the bank, not any room. Exact implementation (inline in `putBank()` vs. a follow-up step) is a `/plan-eng-review` detail; the mechanism itself is now named and feasible against the actual code.
- **Upload validation (decided for v1)**: content-type allow-list (`image/png`, `image/jpeg`, `image/webp`) and a size cap (5 MB, independent of `MAX_BANK_BODY_BYTES`), enforced at the `/api/bank/image` endpoint before writing to R2. Validated against the actual file bytes (magic-number sniffing), not the client-supplied `Content-Type` header — the bucket is public-read, so trusting a spoofed header would let an arbitrary file (e.g. an SVG with an embedded script) be uploaded and publicly served under a false image claim.
- **Broken-image fallback (decided)**: if an image fails to load on `/play` or `/screen` (deleted object, network failure), the question's text and any other content still render — the image area shows a placeholder, never a blank screen or a crashed question. The host is not blocked from judging just because an image failed to load.
- **Upload-time failure (decided)**: if validation rejects the file (wrong type/too large) or the upload/R2 write fails, the bank editor shows an inline error on that question's image field and the question is left in its pre-upload state — no partial or corrupt image reference is saved to the bank.

### R3-1 — clarity

**Problem**

> 'Upload transport (decided)' states /api/bank/image 'writes to R2 and returns the object key,' but the document never specifies what the bank editor actually stores on the question record: the raw R2 object key, or a fully-qualified r2.dev URL. Since 'Serving strategy (decided)' commits to public r2.dev URLs, /play and /screen need a resolvable URL at render time, but the interface between the upload endpoint's return value and the question schema's image field — and where the r2.dev base is joined to the key (client, Worker, or stored pre-joined) — is unspecified.

**Remedy**

> State whether the question schema stores the raw R2 object key or the full public URL, and where (client, Worker, or bank schema) the r2.dev base URL gets prepended.

### R3-2 — feasibility

**Problem**

> The decided serving strategy commits production image delivery to R2's r2.dev subdomain. Cloudflare documents r2.dev as intended for testing/development, without a production SLA and subject to aggressive, undocumented rate limiting — not a domain Cloudflare recommends for serving live production traffic. Since images render during real parties and the entire feature exists to serve the 'lack of narrative immersion' pain point (Q3's 'everyone has fun / good vibe'), a throttled or rate-limited r2.dev response mid-session would trigger the broken-image fallback exactly when the DM-narrated framing needs to land, undermining the design goal the feature was built for.

**Remedy**

> Either explicitly accept and document the r2.dev production-use risk (with a mitigation/monitoring note), or move to a custom domain behind Cloudflare despite the extra one-time DNS/cert step.

### R3-3 — completeness

**Problem**

> The upload flow is two steps: (1) POST /api/bank/image writes the file to R2 and returns an object key, (2) a separate /api/bank PUT persists the question referencing that key. 'Upload-time failure (decided)' only covers the case where 'the upload/R2 write fails' — it does not cover step 1 succeeding while step 2 never completes (network drop, navigation away, bank PUT rejected). In that case the object exists in R2 but is referenced by no question, so none of the three named R2 cleanup triggers apply (deleted question, changed image reference, kind switched away from image) — an object that was never referenced can't be 're-edited' or 'switched away from.' The object is silently orphaned in the public bucket with no path to cleanup.

**Remedy**

> State how objects written to R2 but never successfully attached to a saved question get cleaned up — e.g., only report upload success once the bank PUT is also confirmed, or add an explicit sweep for unreferenced objects.

### R3-4 — completeness

**Problem**

> 'Upload validation (decided for v1)' caps only file size (5 MB) and content type; no constraint or guidance is given on image pixel dimensions or aspect ratio. Success Criteria asserts the image 'render correctly' on both /play (team phones) and /screen (host's big screen), but nothing specifies how an extreme-dimension image (e.g. 6000x800px, still under 5MB) is scaled, cropped, or fit within the existing question layout on either surface.

**Remedy**

> State the intended display/fit behavior (e.g. max-width/max-height with aspect ratio preserved), or explicitly defer it as a named UI implementation detail for eng review, consistent with how the R2 cleanup mechanism was deferred.
