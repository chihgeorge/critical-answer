# Design: ⚔️ 最後衝刺

Generated by /office-hours on 2026-11-08
Branch: main
Repo: chihgeorge/critical-answer
Status: APPROVED
Mode: Builder

## Problem Statement

When the first team enters the boss room, the game changes: every other team now walks into the boss room on its next correct answer (`answerQuestion`'s `entersBoss`). Nobody on stage is told this. The last-place team also has no reason to believe it can still catch up. 最後衝刺 makes that moment visible and gives the last-place team one comeback push.

## What Makes This Cool

The door opening becomes an event the whole room sees. A purple 「⚔️ 魔王門開了！」 banner plays on the reveal of the correct answer that opened it. The owl says the team that trails was given a blessing. The trailing team's phone shows ✨ at the same moment.

## Constraints

- Features are due 2026-11-18; the event is 2026-11-21. No deploy during the event.
- Reuse the event-room blessing (`boon: "blessing"`, `BOON_TEXT`, `screen-boon`, `phone-boon`). No new effect.
- The 🧪 lucky-potion item slot (`docs/designs/lucky-potion.md`) is separate. The blessing does not use it.
- Game state stays in `lib/game-state.ts` as pure functions with unit tests.

## Premises (all agreed)

1. **Trigger.** It fires once per game, the first time any team enters the boss room. A correct answer that reaches the threshold counts, and so does the host's `sendToBoss`. It does not fire when the game starts with `bossThreshold <= 0`, because every team starts in the boss room.
2. **Target.** The target is the team with the lowest 飽足感 (`reward`) among the teams that are not in the boss room after the entry. If several teams tie for lowest, they all get the blessing.
3. **Effect.** The target gets `boon: "blessing"`: half the base reward extra on the next correct answer, boss hits included (`critBonus`, game-state.ts ~780).
   - The blessing replaces a 💀 curse.
   - A team that already has a blessing gets nothing more.
   - A curse that lands later still replaces the blessing: a blessed team that opens a 💀 idol event gets the curse. That is the existing rule (`openEvent` writes the newest boon), and the event reveal shows it.
   - It does not take the 🧪 item slot.
4. **Show.** The big screen shows 「⚔️ 魔王門開了！最後衝刺」 and the owl says one line. The phone uses the existing blessing display.
5. **No trigger.** Nothing happens when the game has only one team, or when no team is left outside the boss room.

## Approaches Considered

- **A: game-state built-in (chosen).** `applySprint(prev, next)` lives in `lib/game-state.ts` and is called from `answerQuestion` and `sendToBoss`. It sets `game.sprint`.
- **B: room-layer detection (rejected).** It needs a new `SPRINT` message type and a resend on reconnect, and its tests would have to go through the room.
- **Banner A: merged into the 「首領出現！」 alarm (rejected).** The banner would show one turn late, when the boss room first comes on screen, not when the door opens.

## Recommended Approach

### State

- `GameState.sprint?: { teamIds: string[] }`.
  - It is set once, when the sprint fires.
  - Its presence is the once-per-game guard.
  - `teamIds` are the blessed teams. The list is never empty: when premise 5 applies, `sprint` stays unset.
- `getSpectatorView` copies `sprint` to the public view, so the screen and phones can name the teams.

### Rule: `applySprint(prev, next)`

It is a pure helper. It fires only when all of these hold:

1. `prev.sprint` is unset.
2. No team in `prev` has `inBoss`.
3. Some team in `next` has `inBoss`.
4. `next.config.bossThreshold > 0`. Guard 2 already implies this (threshold 0 starts every team in the boss room); it stays as a cheap second check.

When it fires:

1. It collects the candidates: the teams where `!inBoss`. Offline teams count too; they are still in the game and the phone shows the blessing when they come back.
2. It returns `next` unchanged if `teams.length < 2` or there are no candidates.
3. It takes the minimum `reward` among the candidates; every candidate with that reward is a target.
4. It sets each target's `boon` to `"blessing"`, which replaces a curse.
5. It sets `sprint: { teamIds }`. A target that already had a blessing is still listed by name, but nothing stacks.

Call sites:

- The end of `answerQuestion`'s correct-room-advance branch.
- `sendToBoss`.

`enterNextBossPhase`'s buzzer pull calls `sendToBoss` while a team is already in the boss room, so the guard keeps it from firing. `openEvent` only enters the boss room when a team is already there, so it never fires either.

### Big screen: new transition kind

- `TransitionSeen` gets `sprint: boolean | null`, with the same rule as `boss`: `null` until the first STATE after connecting (`UNSEEN`), `false` in the lobby and intro (`IN_LOBBY`), `true` once `view.sprint` is present or the game is not playing.
- The type becomes `Transition = … | { kind: "sprint"; names: string[] }`.
- `nextTransition` plays it when this connection saw `view.sprint` absent and now sees it present, live only. A screen that reconnects mid-game never replays it, the same as `open` and `boss`.
- On the `answerQuestion` trigger it plays on the reveal of the correct answer. The 「首領出現！」 alarm still plays later, when the boss room first comes on screen. The reveal blocks `bossOnScreen`, so the two cannot overlap.
- On the `sendToBoss` trigger there is no reveal, so both can be due in the same STATE. The sprint wins; `seen.boss` stays `false`, so the boss alarm plays on the next STATE that has the boss on screen. A `nextTransition` test covers this.
- Layout: the same as the alarm band (`px-alarm-band` and `px-alarm-text` geometry), with the stripes in `--lav2` and `--k` instead of `--warn`.
  - Line 1: 「⚔️ 魔王門開了！」 in `px-title-gold`.
  - Line 2: 「最後衝刺：其他隊答對一題就能進魔王房」.
  - Line 3: 「{隊名、隊名} 獲得 ✨祝福（下次答對多一半）」, truncated.
- Three lines do not fit the alarm's 150px band: the sprint band is 190px tall (`top: 160`). `MS.sprint = 2500`, `STILL_MS.sprint = 1500`, as for the boss alarm.
- It shows for 2.5 s. Reduced motion shows one still frame for 1.5 s.
- Sound (design review D3): a new `SPRINT_FANFARE` in `lib/sfx.ts`, played with `playCue` when the banner starts, as `BOSS_ALARM` is: four quick rising square notes and one held note, about 0.8 s, e.g. `G4 C5 E5 G5` at 0.08 s each, then `C6` for 0.45 s. Same family as `crit`'s trumpet, a different tune. Big screen only.
- On the `sendToBoss` trigger (design review D1) the banner plays over whatever is on screen, a question being answered included. The question and its clock carry on underneath; the banner only covers, like the boss alarm.
- The sketch is `.gstack/previews/sprint-sketch.png` (local only, not committed), panel B. Its name plates are drawn for illustration only; the big screen has no name-plate row during play.
- Names on line 3 are joined with 「、」 and truncated like the alarm's name line. An already-blessed target is still named: the banner says the room's blessing went to the trailing team, and it does not stack.

### Owl line

- Text: 「🦉 {進門隊}進魔王房了！{隊名}獲得祝福！」. Budgets count UTF-16 units, as `sanitizeText` does (🦉 is 2), so the fixed text is 14 units. `MAX_EDIT_LINE` is 40 and a team name can be 20, so the names are capped, not the line: the entering team's name to 10 units and the joined target names (「、」) to 14, each including its 「…」 when cut, and cut on code-point boundaries so an emoji is never split. The line is at most 38 units and always keeps 「獲得祝福！」. A unit test uses two 20-character tied names.
- On the `sendToBoss` trigger there is no answer narration to append to, so there is no owl line; the banner carries the moment. A room test covers this.
- It is appended to the current narration with the same mechanism as lucky-potion E5. If the narration has not arrived yet, the line is held until it lands. The line is sanitized with `MAX_EDIT_LINE` and dropped if the game finishes. Implement one shared helper for both features.

### Phone and host

- Phone (design review D2): a blessed team's phone shows a 3-second card when the sprint is seen live.
  - A `Panel tone="turn"` centred over the phone screen: 「✨ 你們拿到祝福！」 (24px), then 「魔王門開了：下次答對多一半」 (14px).
  - It disappears by itself after 3 s and needs no tap. It never covers a button for longer than that and takes no input (`pointer-events: none`).
  - `navigator.vibrate?.(80)` once, where supported.
  - `role="status"`, so screen readers read it. It does not animate, so reduced motion changes nothing.
  - Live only, with the same rule as the screen's transition: a phone that (re)connects after `view.sprint` is set does not show it.
  - Afterwards the existing `phone-boon` line 「✨ 祝福：下次答對多一半」 stays on the team card.
- Host: no new UI. The existing boon indicators show it.
- Big screen outside the banner: the `screen-boon` chip shows on the question panel when the blessed team's turn comes.
- Map pawn mark (design review D4): a 12px ✨ above the pawn's tag in `components/map-strip.tsx` while the team holds a blessing, and 💀 while it holds a curse, for any boon, the event room's included. It uses the same spot and method as lucky-potion D1/D11's 🧪 and never changes the tag's width. A team holding a boon and a potion shows both side by side.

## Success Criteria

- When the first team enters the boss room in a 3-team game:
  - the lowest-飽足感 team outside the boss room sees the 3-second ✨ card on its phone, then keeps the `phone-boon` line;
  - that team's map pawn shows ✨;
  - the screen plays the purple banner once, with `SPRINT_FANFARE`;
  - the owl says the line (answer trigger only; `sendToBoss` has none).
- That team's next correct answer pays +50% of the base reward. Usually that is the room answer that walks it into the boss room. A team that enters without a correct answer (`sendToBoss`, the buzzer pull) keeps the blessing for its first boss hit; a unit test covers that.
- A reconnecting screen does not replay the banner.
- Unit tests cover:
  - the trigger guards (threshold 0, one team, no candidates, second entry);
  - a tie;
  - a curse replaced by the blessing;
  - an existing blessing that does not stack;
  - `sendToBoss` as the trigger;
  - a blessed team that opens a curse event ends up cursed.
- `nextTransition` tests cover live and reconnect.
- `npm run check:bundle` passes. e2e runs in CI only.

### Architecture

```
answerQuestion(correct) ──┐                       ┌─> GameState.sprint = { teamIds }
sendToBoss(host / buzzer) ┴─> applySprint(prev, next) ─┤   targets' boon = "blessing"
                                                   └─> unchanged (guards fail)
GameState ──getSpectatorView──> view.sprint (public) ──STATE──┬─> screen: nextTransition → sprint banner + SPRINT_FANFARE
                                                              ├─> phone: sprintSeen rule → 3 s card + vibrate
                                                              └─> map-strip: pawn ✨/💀 from view.teams[].boon
room: correct-answer narration for eventId ──appendLine helper (shared with lucky-potion E5)──> NARRATION rev+1
game end ──gameLog()──> teams[].sprintBlessed (and the potion PR's potionsGiven / potionsDrunk)
```

### Decisions

- **E1 State and snapshot.** `GameState.sprint?: { teamIds: string[] }` is optional. An old snapshot has no field and means "not fired"; a restored game that already has a team in the boss room fails guard 2, so it never fires late. No `SCHEMA_VERSION` bump: no field changes meaning.
- **E2 Call sites.** `applySprint(prev, next)` runs once at the end of `answerQuestion`'s correct branch and at the end of `sendToBoss`. `enterNextBossPhase`'s buzzer pull goes through `sendToBoss`, but a team is already in the boss room, so guard 2 holds. `openEvent` is not a call site.
- **E3 Live-only rule, shared.** `lib/transitions.ts` gets a pure `sprintSeen(seen, view)` rule used by both the screen (`TransitionSeen.sprint`) and the phone card: `null` until the first STATE after connecting, so a (re)connect after the sprint never plays it. One unit test file covers both.
- **E4 Game log (user decision, 2026-11-08).** `GameLog.teams[]` gets `sprintBlessed: boolean`. The lucky-potion PR adds `potionsGiven: number` and `potionsDrunk: number` the same way (its doc's open question is resolved by this). The fields are additive; old logs read as `false` / `0` where read.
- **E5 Owl line.** Appended through the lucky-potion E5 helper to the narration of the eventId of the answer that opened the door. Whichever PR lands first builds the helper; the other reuses it.
- **E6 Names on the client.** `view.sprint.teamIds` are ids; the screen and phone resolve names from `view.teams` and apply the truncation rules client-side for the banner. The owl line's caps are applied in the room (it builds the line).
