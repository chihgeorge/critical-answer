# Design: DM 語音旁白（瀏覽器 TTS）

Generated by /office-hours on 2026-09-23
Branch: main
Repo: chihgeorge/critical-answer
Status: APPROVED
Mode: Startup

## Problem Statement

大螢幕現在只顯示旁白文字，沒有語音。這個功能想讓旁白從「要看的文字」變成「大家一起聽的場景」。

## Demand Evidence

**沒有。** 明確問過：目前沒有玩家或朋友主動提過「要是有聲音就好了」。這是創辦人自己想加的功能，不是被要求的。

## Status Quo

現在 host 自己會把大螢幕上的旁白文字念出來（給玩家聽）。這代表「有人聲把旁白說出來」這件事本身已經被人力解決了，不做這個功能不會讓遊戲卡住或體驗中斷。

真正想要的不是「填補一個空缺」，而是想要更氛圍感的體驗——不是 host 太累或分心的問題。

**工作流程改變（spec review 找到的缺口）：** TTS 上線後，host 不用再念旁白——如果兩者同時發生，玩家會同時聽到 TTS 語音跟 host 念的聲音疊在一起，反而破壞「大家一起聽場景」的目標。這是社交層面的改變，不只是技術加法：host 需要知道自己不用再念了。

## Target User & Narrowest Wedge

目標使用者就是創辦人自己，每次聚會的主辦人/host。想要的是「大家一起聽的場景」而非功能性需求。

最小可行版本：瀏覽器內建 Web Speech API（zh-TW 聲音），接在現有的 NarrationEvent 事件流下游，一個開關可以關掉。

## Constraints

- 零額外費用（不接付費雲端 TTS）
- 不能動到房間邏輯或現有的敘事事件流
- 遊戲本身不因旁白而暫停（STATE 和動畫都是立即更新，旁白是「順便播放」）
- 旁白句子短（約 15-40 字），現有 host 已經在即時念，TTS 播放時間不會拖慢節奏

## Premises

1. 這是品味驅動（taste-driven）不是需求驅動（demand-driven），但成本低到可以接受 — 同意
2. 現有的做法（host 手動念）已經能正常運作，所以不做也不會阻斷遊戲 — 同意
3. 現有的 NarrationEvent 事件流已經把旁白文字送到 /screen，TTS 只需要接在下游消費這些事件，不需要動到房間邏輯 — 同意

第二意見（跨模型交叉驗證）：略過，功能太小、風險太低，不需要。

## Approaches Considered

### Approach A: 瀏覽器內建 TTS（最小可行版本）— 選定
直接在 /screen 頁面訂閱 NarrationEvent，新旁白到來就呼叫 `speechSynthesis.speak()`（zh-TW 聲音），一個開關按鈕存 localStorage。新旁白到來時取消上一句還沒念完的（避免重疊）。
- 成本：人工約 0.5 天 / CC 約 20 分鐘
- 零額外費用、零外部依賴
- 音質未知：多數瀏覽器內建中文語音偏工具人腔，不是說書人聲音——這是待驗證假設，不是已知限制
- **語音清單非同步載入（spec review 找到的缺口）：** `speechSynthesis.getVoices()` 在頁面剛載入時常常是空的，要等 `voiceschanged` 事件才會填入實際語音清單。第一句旁白如果在語音清單載入前就 `speak()`，可能會靜默失敗（沒聲音也沒錯誤）。實作要等 `voiceschanged`（或至少確認清單非空）才開始播放。
- **Safari/iOS 手勢限制（spec review R1-4/R2-1 找到的缺口，round 2 修正）：** 部分瀏覽器（尤其 Safari/iOS）會把語音輸出鎖在「使用者手勢觸發的呼叫」之後才解鎖——關鍵是解鎖的那個 `speak()` 呼叫本身要在點擊事件處理函式裡「同步」執行，不是隨便有一次點擊就算數。開關按鈕的 `onClick` 要親自呼叫一次 `speechSynthesis.speak()`（唸一個空白或極短的暖身字串）才算真正解鎖，不能只是把偏好設定存進 localStorage 就當作完成——如果只存偏好，之後某句旁白到來時才第一次呼叫 `speak()`，那次呼叫已經不在使用者手勢的同步呼叫鏈裡，Safari/iOS 上可能還是靜默失敗。
- **`then` 行也要念（/plan-eng-review Outside Voice 找到的缺口）：** `NarrationEvent` 其實常常有兩行——`line`（判題結果）跟 `then`（下一隊的提示，例如「接下來輪到隱藏隊了！」），螢幕上兩行都會依序顯示（見 `components/pixel.tsx` 的 `Sequence`，間隔 `LINE_PAUSE_MS`＝2200ms）。TTS 依 `lib/narration/client.ts` 的 `linesOf(narration)` 依序念出陣列裡的每一行，不是只念 `narration.line`——否則每次輪到下一隊時，語音會漏掉那句轉場提示。
- **防重播機制改為純記憶體版（/plan-eng-review Outside Voice 找到的缺口，取代原本的 localStorage 版）：** 原本設計用 localStorage 記「已念過的 eventId」，但 `eventId`（`dungeon-room.ts` 的 `eventSeq`）在每次 `reset()`（新遊戲、房間過期、伺服器重啟）都會歸零，而房間代碼可以被重用——用房間代碼+eventId 當 key，會把新遊戲的旁白誤判成「舊遊戲已經念過」而靜音。改用更簡單的機制：**不存 localStorage**，只用一個記憶體變數（`useRef`）記住「這次頁面連線/掛載後，第一個收到的 NARRATION 或 EPILOGUE 不念——那一定是 `onConnect` 重送的舊快照，之後收到的才是真正的新事件，全部念」。這個規則同時解決 WS 重連、整頁重新整理、房間代碼重用三種情況，且完全不需要考慮 `roomEpoch` 或跨頁面持久化，程式碼比原本的 localStorage 版更少。
- **語音比對用前綴/包含，不是精確比對（/plan-eng-review Outside Voice 找到的缺口）：** 不同瀏覽器/OS 回報的中文語音 `lang` 標籤不一致（`zh-TW`、`zh-Hant-TW`、`cmn-Hant-TW`、`zh_TW`，某些 Android WebView 甚至只有顯示名稱沒有可靠的 lang 標籤）。挑選語音時用「`lang` 開頭是 `zh` 且包含 `TW`/`Hant`」這類寬鬆比對，不能只做 `voice.lang === "zh-TW"` 的精確比對——否則會在明明有堪用中文語音的瀏覽器上誤判成「找不到」而整個啞掉。
- **`LOBBY` 訊息（房間重置）要順便取消正在播放的語音（/plan-eng-review Outside Voice 找到的缺口）：** `screen/page.tsx` 的 `case "LOBBY"` 會把 `narration`/`epilogue` state 清空（伺服器重啟、新遊戲），畫面上也會顯示「伺服器重新啟動，遊戲已重置」的提示。如果這時語音正念到一半，設計裡原本只有「新 NARRATION 到來時取消上一句」這個觸發點，沒有涵蓋 `LOBBY` 重置——這裡也要呼叫一次取消，不然舊遊戲的旁白會在畫面都重置後還繼續念完。

### Approach B: 完整架構版（設定面板）
加語速、音高、可選聲音等設定面板。目前沒人要求這些微調選項，先不做。

### Approach C: 預錄音檔 + AI 動態旁白 fallback 純 TTS
固定腳本句事先用付費雲端 TTS 生成高品質音檔，只有 AI 動態生成的旁白才用瀏覽器 TTS。音質會明顯更好，但需要額外的音檔生成流程、存檔、可能的外部 API 費用——遠超出這個功能該花的成本量級。

## Recommended Approach

Approach A。先用免費版本上線，實際聽聽看 zh-TW 語音品質如何，再決定要不要往 B 或 C 升級。

## Open Questions

- 瀏覽器內建 zh-TW 語音的實際音質如何（工具人腔 vs. 可接受）——只有上線聽過才知道，這是 Assignment 的內容。
- **取消頻率的實際體感（spec review 找到的缺口）：** 設計已經決定「新旁白到來時取消上一句還沒念完的」，但沒評估這在真實遊戲節奏下多常發生、玩家聽起來會不會覺得句子常常被「咬斷」。畢竟這功能的重點就是氛圍，如果常常被咬斷，氛圍感反而會被破壞。這點也列進 Assignment：上線後要順便觀察取消發生的頻率是否影響體感。

## Success Criteria

- 新旁白事件到來時，語音會依序念出 `narration.line` 和（若存在）`narration.then` 兩行——跟畫面上 `Sequence` 顯示的內容一致，不會漏掉轉場提示（/plan-eng-review Outside Voice 找到的缺口）
- 有明顯的開關可以關閉語音，**預設關閉**（第一次打開 /screen 時，語音不會自動開始播放；使用者主動點開才開始，這個點擊同時解決 Safari/iOS 的手勢限制——開關偏好可以存 localStorage，這個跟下面的防重播機制是兩回事）
- 語音清單載入完成（`voiceschanged` 觸發或清單非空）後才開始播放，不會對還沒準備好的語音清單呼叫 `speak()`
- 挑選語音時用寬鬆比對（`lang` 開頭 `zh` 且包含 `TW`/`Hant`），不是精確比對 `zh-TW`——避免在明明有堪用語音的瀏覽器上誤判成「找不到」（/plan-eng-review Outside Voice 找到的缺口）
- 找不到中文語音時，安靜地不播放語音（不報錯、不用其他語系語音硬念中文字）——旁白文字本身還在，不影響閱讀
- 新旁白（或 `LOBBY` 房間重置）到來時，上一句還沒念完的語音會被取消，不會重疊（/plan-eng-review Outside Voice 找到的缺口：`LOBBY` 重置也要觸發取消）
- **不重播已經念過的舊旁白（改用純記憶體機制，取代原本的 localStorage 版）**——`/screen` 連線或重新整理時，server 會重送 `lastNarration`/`epilogue`（見 `dungeon-room.ts` 的 `onConnect`）。用一個記憶體變數（`useRef`）記住「這次連線/掛載後第一個收到的 NARRATION 或 EPILOGUE 不念」，之後收到的都念。這個規則同時涵蓋 WS 重連、整頁重新整理、房間代碼被新遊戲重用（`eventId` 歸零）三種情況，不需要 localStorage、也不需要比對 `roomEpoch`（原本的 localStorage-only-by-roomCode 設計在房間代碼重用時會誤判新遊戲的旁白為「已念過」，/plan-eng-review Outside Voice 找到這個真實 bug 後改用這個更簡單也更正確的機制）
- **host 用「⚙ 更多」修正目前旁白時（`HOST_EDIT_NARRATION`）會重念一次**——這個訊息沿用同一個 eventId、只是文字內容變了，跟「新 eventId 到來」不是同一種情況。TTS 要把它當成內容變更事件：取消目前還在播的語音，重新念出修正後的文字（spec review R2-3 找到的缺口）
- 房間狀態轉換與畫面動畫，不管語音有沒有播完、有沒有開啟，都照原本的時機觸發（不會被語音播放卡住或延後）
- **瀏覽器完全沒有 `speechSynthesis` API 時，開關按鈕直接不渲染**（不是顯示但 disabled）——極舊瀏覽器或某些嵌入式 WebView 不支援這個 API，使用者不該看到一個點了沒反應的按鈕（/plan-eng-review Architecture 找到的缺口）

## Reviewer Concerns

Stop: CONVERGENCE

### R2-1 — feasibility

**Problem**

> Success Criteria and Approach A claim the toggle's on-click satisfies Safari/iOS's user-gesture requirement and 'incidentally unlocks' audio for all future speak() calls ('使用者點下「開啟語音」按鈕那一下，就是瀏覽器要求的使用者手勢，順便解鎖音訊'). Safari's unlock is tied to the audio-producing API call itself running synchronously inside the gesture handler, not merely to any click occurring on the page. The document never states that the toggle's click handler itself invokes speechSynthesis.speak() (even a silent/priming utterance); if the handler only flips a stored preference, later asynchronous speak() calls triggered by a NarrationEvent arriving minutes later may still be blocked on Safari/iOS, silently producing no audio.

**Remedy**

> Specify that the toggle's onClick handler itself calls speechSynthesis.speak() synchronously (e.g. an empty priming utterance) to perform the actual unlock, not just record a preference — or confirm via testing on the host's real device/browser that a bare click suffices, and record that verification in the document.

### R2-2 — consistency

**Problem**

> Success Criteria claims '頁面重新整理或重新連線時，不會把已經播過的舊旁白重播一次', but the described mechanism only tracks 'the first new eventId seen this connection' in client-side memory. A hard page reload resets that in-memory tracking entirely, so when onConnect resends lastNarration (confirmed in lib/room/dungeon-room.ts: 'if (this.lastNarration) this.sendTo(conn, { type: "NARRATION", ...this.lastNarration })') after a reload, the freshly-loaded client sees that eventId for the first time this session and would speak it again — exactly the double-narration the criterion claims to prevent for the page-reload case, even though it is fully solved for the WebSocket-reconnect-without-reload case.

**Remedy**

> Persist the last-spoken eventId across reloads (e.g. in localStorage, alongside the existing toggle preference) so a hard refresh can also recognize and skip an already-spoken eventId, or narrow the success criterion's wording to only claim coverage for reconnects that don't involve a full page reload.

### R2-3 — completeness

**Problem**

> The existing HOST_EDIT_NARRATION flow (lib/room/dungeon-room.ts handleEditNarration) re-broadcasts a NARRATION message with the SAME eventId but corrected text when the host edits the currently-shown line. The design's speak-once-per-eventId rule and cancel-on-new-event rule are both keyed to the eventId changing, so this case — content changing under an unchanged eventId — is unaddressed: it's unspecified whether the host's correction gets spoken, is silently ignored (leaving the TTS audio saying something different from the now-edited on-screen text), or something else.

**Remedy**

> State the intended TTS behavior when HOST_EDIT_NARRATION updates the currently-displayed line: re-speak the corrected text (cancelling any in-progress utterance first), or explicitly document that edits are not re-spoken since only the eventId-based rule governs playback.

### R2-4 — completeness

**Problem**

> The document scopes TTS to 'NarrationEvent'/NARRATION-type messages and defines its reconnect-dedup entirely by eventId, but the game's EPILOGUE message (broadcast once on game finish, and resent verbatim to any connecting/reconnecting client via onConnect's 'if (this.epilogue) this.sendTo(conn, { type: "EPILOGUE", text: this.epilogue })') carries no eventId at all and is never mentioned anywhere in the design. It's unclear whether the epilogue — arguably the most narratively significant line in the whole session — is meant to be spoken by TTS at all; if it is, the eventId-based reconnect-dedup mechanism the design specifies cannot apply to it, so every reconnect or reload after game-over would re-speak the epilogue in full.

**Remedy**

> State explicitly whether EPILOGUE text is included in what TTS speaks; if included, specify a separate dedup mechanism for it (it has no eventId to key on) so it isn't re-spoken on every reconnect/reload.

### Prior finding evidence

**R1-4 → R2-1 (persisting)**

> Approach A and Success Criteria assert the toggle click alone resolves the Safari/iOS gesture gate ('使用者點下「開啟語音」按鈕那一下...順便解鎖音訊'), but never specify that the click handler itself performs a speak() call — the actual unlock mechanism Safari requires. This is the same unresolved feasibility risk from round 1, now surfaced as an underspecified/likely-incorrect fix rather than an unaddressed one.

**R1-6 → R2-2 (persisting)**

> Success Criteria's reconnect bullet explicitly claims coverage of '頁面重新整理' (page reload), but the cited mechanism (only speak 'eventId 這次連線後第一次看到' via in-memory client state) cannot survive an actual page reload, which wipes that in-memory tracking — so the specific page-reload case this finding named remains unmet even though the WS-reconnect-without-reload case is now solved.
