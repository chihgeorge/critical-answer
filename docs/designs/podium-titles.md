## Problem Statement

遊戲結束時只有前三名上台，加上一張「本場大成功王」卡。8 隊的場次裡，第 4–8 名在結算畫面上完全沒被點名，手機上只看到「感謝參與！」。活動在 2026-11-21，功能要在 11/18 前做完。

## What Makes This Cool

- 每一隊都會被點名一次以上。旁白一個一個頒稱號：「💀 詛咒磁鐵……隔壁老王！」，黃卡上寫理由「被詛咒 3 次」。
- 稱號從這場真的發生的事算出來：吃最多料理、逃跑最多次、被詛咒最多。全場會笑，因為大家剛剛親眼看到那些事。
- 節奏照 Mario Party 的加分星：先唸獎名，停頓，再公布得主。全部稱號頒完，最後才揭曉前三名。

## Constraints

- 不加分，不改名次（`rankTeams` 照舊只看飽足感）。
- 11/18 前合併，活動當天不部署。
- 最多 8 隊（`MAX_TEAMS`）。
- 大螢幕 960×540。DESIGN.md：不做補間動畫，只用硬切。
- 題庫資料不能進瀏覽器 bundle。稱號只用隊伍統計，不碰 `BANK`。
- AI 旁白可能關掉或失敗，每一段都要有腳本保底（沿用 runner 逐段換腳本的機制）。

## Premises

1. 揭曉順序：先頒全部稱號，每個稱號一拍；稱號頒完，照現在的流程公布第三、二、一名（同分擲骰照舊）。
2. 大成功王變成稱號之一，跟其他稱號一起頒。不再單獨一拍，右側的 CritKingCard 拿掉。
3. 每個數據稱號給數值最高的隊。並列第一的隊都拿（同一拍一起唸）。數值 0 不頒。一隊可以拿好幾個。
4. 頒稱號時不寫名次，榮譽榜也不標名次，前三名的懸念留到最後。
5. 一個稱號都沒拿到的隊：在數據稱號之後，由 AI 依它這場的數據現編一個稱號，每隊一拍（像 Mario Party 的安慰獎）。AI 關掉或失敗時，用保底「🛡️ 堅持到最後的冒險者：撐了 N 回合」。
6. 不加分、不改名次。🧪 藥水成癮要等幸運藥水 PR 合併（`potionsDrunk` 欄位存在）才會出現。

## 稱號清單

| 稱號 | 誰拿 | 資料來源 |
|---|---|---|
| 🗺️ 探險家 | 開最多事件房（任何場景） | `team.events.length` |
| ✨ 女神的寵兒 | 事件房祝福最多 | `events` 裡 `blessing` 的次數（`great` 只給飽足感、沒有祝福，不算） |
| 💀 詛咒磁鐵 | 事件房詛咒最多 | `events` 裡 `curse` ＋ `bad`（算命「凶」也給詛咒，`openEvent` lib/game-state.ts:1258）的次數 |
| 🤢 腐肉品嚐家 | 吃到腐肉最多 | `events` 裡的 `rotten` 次數 |
| 🏃 逃跑大師 | 答錯逃跑最多 | 新欄位 `team.flees`，每次 `incorrect-flee` 都加一（一般房和魔王房都算） |
| 🧪 藥水成癮 | 喝最多幸運藥水 | 藥水 PR 的 `potionsDrunk`。這一列的程式碼由後合併的那個 PR 加（見 Dependencies）；執行時缺值當 0 |
| 🍲 大胃王 | 吃最多料理 | `team.dishes.length` |
| ⚡ 閃電突擊 | 靠答對最少回合進魔王房 | `team.bossAt.turns`，越少越好。只算靠答對進門的隊：`bossAt` 加 `earned: true`，只在 `answerQuestion` 答對進門時寫；`sendToBoss`（主持人送、搶答階段拉人）和門檻 0 的 `createGame` 不寫。有 `earned` 的 turns 至少 1，所以不會碰到「0 不頒」。沒有隊靠答對進門就不頒 |
| 🎲 大成功王 | 擲出最多次 20 | `team.natural20s`（取代現在的 crit beat） |

- 頒獎順序照上表，大成功王壓軸。最後是 AI 稱號（每隊一拍，照隊伍順序）。
- 最後衝刺給的祝福不是事件房，不算進 ✨。
- 舊存檔沒有的欄位（`flees`、`events`、`dishes`、`natural20s`、`bossAt.earned`）一律當 0／沒有。

## Approaches Considered

- **A 不接 AI**：沒拿到稱號的隊一律給保底稱號。約 1 小時。不採用，因為使用者要 AI 現編的稱號。
- **C 另開 AI 呼叫＋手機稱號卡**：多一個等待點。約 3 小時。不採用。
- 第 4–8 名的放法另外比較過三種：Kahoot 式（各自手機顯示名次）、兩側榮譽榜、標題下一排名牌。使用者最後選 Mario Party 式「逐一宣布」，這三種都不採用。

## Recommended Approach

**B：併進後記呼叫。** 約 2 小時（CC），再加上把頒稱號改成每個稱號一拍的工作。

1. **計算與存放**：
   - `lib/podium.ts` 加純函式 `awardTitles(teams)`，回傳依頒獎順序排好的 `Award[]`，每筆是 `{ id, icon, title, teamIds, reason }`。數據稱號的 `reason` 由程式產生，例如「被詛咒 3 次」。
   - `critKing`、`critLine` 拿掉，由 `awardTitles` 的 🎲 那一筆取代。
   - `GameState` 加 `awards?: Award[]`：在 `finishGame` 跟 `ranking` 同時算好，存進 snapshot，重連時直接讀。
   - `GameState` 加 `consolations?: { teamId, icon, title, reason }[]`（`icon`：AI 稱號 🌟、保底 🛡️，稱號文字不帶圖示）：沒拿到稱號的隊各一筆。`finishGame` 先放保底，後記台詞回來後由房間換成通過檢查的 AI 稱號（跟現在後記台詞到了才產生 `beats` 同一個時間點）。
2. **拍子**（`lib/podium.ts`）：
   - `Beat` 的 `crit` 換成 `{ kind: "award"; line; icon; title; names; reason }`。AI 稱號也用這個 kind，`icon` 是 🌟；保底稱號的 `icon` 是 🛡️（設計審查 D4）。
   - `revealBeats` 的順序：所有 award 拍（數據稱號，接著是安慰稱號），然後名次拍 3→2→1；同分擲骰的拍照舊插在名次前。
   - 每個 award 拍 2.5 秒（`beatMs`）。
   - `revealCalls` 不再回傳 `critKing`，改回傳 `titles`：沒拿到稱號的隊和它們的 facts。
3. **台詞長度**：
   - 新常數 `MAX_AWARD_LINE = 28`（UTF-16 單位），一行放得下。來源：頒獎台的對話框不是 compact，字級 27px、文字寬 786px（同 `EPILOGUE_PAGE_CHARS` 用的 786px），一行 floor(786 / 27) = 29 個字，留 1 個給標點。
   - 稱號拍的台詞只有「{icon}{title}……{隊名}！」，不含 `reason`（設計審查 D2）。理由只寫在黃卡上。這樣大螢幕在 2.5 秒內唸得完，不會被下一拍切掉。
   - 超過 `MAX_AWARD_LINE` 時，並列就把隊名換成「{第一隊}等 N 隊」，單隊就截斷隊名。用單元測試確認：20 字隊名、所有稱號、並列 2 隊時都不超過。
   - 名次拍照舊用 `MAX_CALL_LINE = 20`。
4. **數據稱號全用腳本**：
   - 數據稱號的台詞全部由程式產生，不送進 AI。大成功王以前由 AI 寫，現在也改成腳本。
   - 這樣 `EpiloguePart` 的 `crit` 直接拿掉，不另加 award 段。
5. **AI 安慰稱號**（只給沒拿到數據稱號的隊）：
   - 後記事件拿掉 `critKing`，改成 `titles?: { team: string; facts: TitleFacts }[]`。`EpiloguePart` 加 `{ kind: "title"; team; facts }`，排在名次段前面。
   - `TitleFacts` 只放這些欄位：回合數 `turns`、吃到的料理數、逃跑次數、事件房結果（場景＋結果的中文名）、大成功次數、有沒有進魔王房。**不放** reward、飽足感、score、名次，也不放別隊的資料。
   - 輸出格式：每段一行「稱號｜理由」。稱號 ≤ 10、理由 ≤ 16（UTF-16 單位）。用第一個「｜」切；切不出來、任一邊是空的或超長，這段就換保底。
   - 念出來的台詞由程式組：「{icon}{稱號}……{隊名}！」（AI 🌟、保底 🛡️），理由只寫在黃卡上，套第 3 點的長度規則。
   - runner 的檢查（`fitsPart` 的 title 分支）：
     - 不能有名次字眼（同現在 crit 段的規則：冠軍、榜首、奪冠、第 N 名）。
     - 不能寫到別隊隊名。例外：別隊隊名如果是自己隊名的一部分（例如自己是「隔壁老王」、別隊是「老王」），就不檢查那一隊。
     - 不檢查「必須寫自己隊名」，因為隊名是程式加上去的。
   - 保底：「🛡️ 堅持到最後的冒險者」＋理由「撐了 {該隊自己的 turns} 回合」。
6. **大螢幕**：
   - 頒稱號那拍：中間一張 `--turn` 黃卡，寫稱號、角色、隊名和理由。並列時最多寫 2 個隊名，其餘寫「等 N 隊」。隊名完整寫出，一隊最多換兩行；並列時每隊一行（設計審查 D5）。
   - 音效（D3）：稱號拍開頭放 `SFX.correct`，🎲 那拍放 `SFX.crit`。
   - 不留榮譽榜（設計審查 D1）：下一拍黃卡直接換人，最後一個稱號拍結束後黃卡硬切消失。結算畫面只有台階、標題、答案卡和後記，跟現在一樣。CritKingCard 拿掉，右側空著。
   - 原因：8 隊常有 9–10 個稱號（最壞 17 個），側邊塞不下，還會撞到「最後一題正解」卡。
7. **遊戲紀錄**：
   - `teams[].titles: string[]` 只記數據稱號的 id，例如 `["flees","curse"]`。
   - 遊戲紀錄是 `finishGame` 當下寫的，那時 AI 稱號還沒出來，所以 AI 稱號和保底都不記。
8. **手機**：維持「冒險結束！看大螢幕 📺」，不加稱號卡。`/play` 只用 `revealNow`，不碰 `Beat`，所以不用改。

### R2-1 — feasibility (blocking)

**Problem**

> The derivation of MAX_AWARD_LINE uses the wrong box measurements. The design says the dialog box text is 24px and one row is (960 − 36 − 70 − 14 − 24) / 24 ≈ 34 characters. In the code, the podium DialogueBox (app/room/[code]/screen/page.tsx, style left 18 / right 18) is not compact, so components/pixel.tsx gives it fontSize 27 and padding "12px 22px 10px 116px". The text width is 960 − 36 − 116 − 22 = 786 px, the same 786 px that the EPILOGUE_PAGE_CHARS comment in lib/podium.ts uses. One row at 27px holds floor(786 / 27) = 29 characters, not 34. A 32-unit line wraps to two rows, so the claim that the line fits in one row is false. Only the epilogue switches the box to 22px; the beat lines are read at 27px.

**Remedy**

> Recompute the limit from the real box: 27px font and 786 px text width give 29 characters per row. Keep one character spare as EPILOGUE_PAGE_CHARS does, which gives MAX_AWARD_LINE = 28 for one row. Or allow two rows on purpose, and confirm that the taller box still stays under the podium (bottom 130). Then run the unit tests (20-character names, every title, 2-way ties) against the corrected number.

### R2-2 — clarity (minor)

**Problem**

> The fallback title has the 🛡️ icon, but section 2 says the consolation award beat always uses the 🌟 icon, and section 5 builds the spoken line as 「🌟{稱號}是……」. The consolations entry `{ teamId, title, reason }` has no icon field. The design does not say whether the fallback is read as 🌟 or 🛡️, or whether 🛡️ is part of the title text, which would give 「🌟🛡️ 堅持…」.

**Remedy**

> Say which icon the fallback uses. Either add `icon` to consolations, or drop 🛡️ and use 🌟 for every consolation.

### R2-3 — clarity (minor)

**Problem**

> openEvent (lib/game-state.ts:1285) also writes bossAt when a team opens an event after another team is already in the boss room. The design lists which paths do not write `earned` (sendToBoss, createGame), but it does not name this path. Under the 'only answerQuestion' rule, a team that walks into the boss room through an event is not counted for ⚡. The behavior follows from the rule, but it is implicit.

**Remedy**

> State that an entry through openEvent does not set `earned`, and add a unit test for it.

### R2-4 — clarity (minor)

**Problem**

> A raw title segment 「稱號｜理由」 can be up to 27 units long. fitsPart tells a story apart from a call because the story is longer than MAX_CALL_LINE (20), and epilogueCandidates keeps the last raw line as the story when the model returns too few lines. A misaligned title line of 21 to 27 units can therefore pass as the story.

**Remedy**

> Make the story check reject a line that contains 「｜」, or require the story to be longer than the longest title segment.
