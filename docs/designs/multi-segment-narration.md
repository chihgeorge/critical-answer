## Problem Statement

The host wants narration to feel more immersive — more of a story unfolding, less a single short caption per turn.

## Demand Evidence

Pushed hard on this. The user's first answer ("someone complained it was too short") did not hold up — under one push, they admitted it was actually vague, not a specific remembered complaint. There is no demand evidence. This is the host's own taste call.

## Status Quo

Players already compensate for short narration themselves — banter, in-person reactions, their own commentary. The status quo works; nothing is broken for players today.

## Target User & Narrowest Wedge

Q3 revealed the real answer: the host themselves, running the sessions, is the one who cares most about narration length — not any specific player. The user was told this directly and chose to build for players anyway (see Premises below), with an articulated reason: "我想讓玩家也真的感受得到，不只是我自己知道" (I want players to actually feel it too, not just me).

## Constraints

- The per-line narration cap (`MAX_LINE = 50`, prompt asks for ~28 chars/line) was deliberately tuned DOWN in a prior engineering review (E4 CEO plan) specifically to protect turn-based multiplayer pacing — other teams are waiting while one team's turn plays out.
- `DialogueBox`'s typewriter animation runs at a fixed 45ms/char; `LINE_PAUSE_MS = 2200` between segments. More segments = proportionally longer total playback time per turn.
- Game logic does NOT block on narration playback — `handleHostJudge` isn't awaited by the message dispatcher, so the host can judge the next question before narration finishes animating on clients. A fast-judging host already can (and does, today) cut off an in-progress narration sequence when the next one arrives — this is pre-existing behavior, not something this change introduces, but more segments makes it easier to trigger.
- `NarrationState` (`lib/narration/client.ts`) and the wire protocol (`lib/protocol.ts`) currently hard-code a 2-slot shape (`line` + optional `then`). Supporting 3-4 segments requires widening this to an array end-to-end: protocol message type, `runner.ts`'s `TranscriptEntry`, `client.ts`'s `NarrationState`/`linesOf()`, and `lib/narration/tts.ts`'s `SpokenNarration` (the TTS feature shipped this session also consumes this exact shape and will need matching changes).
- This is not a mechanical type-widening exercise — the content-producing layers are not generic N-slot machinery today. `lib/narration/scripted.ts`'s fallback is structurally two distinct things (`line()` = the result, `nextLine()` = a turn-transition prompt, each drawn from its own hand-written variant pool). `lib/narration/llm.ts`'s `buildPrompt()` hardcodes an exact two-output ask ("輸出兩行...第一行：交代剛剛發生的事...第二行：轉向下一隊"). Neither has any authored content or prompt language today for what a 3rd or 4th segment would even say — that's new authoring work, not a type change.
- `HOST_EDIT_NARRATION` (`lib/protocol.ts`, `MAX_EDIT_LINE = 40`) lets the host live-edit the current narration from `MoreDrawer` — but it only ever edits `narration?.line`, the first segment. The host UI has no notion of which segment a given client is currently displaying (that timing lives client-side in `Sequence`, decoupled from the host). At 3-4 segments, "the line now on screen" becomes ambiguous for this feature.
- `DEFAULT_HOLD_MS = 3000` (the server's wait budget before falling back to scripted) was tuned against 1-2 segment LLM responses ("answers took up to 1.9s once every line has two parts," per the code comment in `runner.ts`). A 3-4 segment completion is a longer generation — plausibly pushes latency closer to or past the existing hold, increasing scripted-fallback frequency and undermining the whole point of the change (AI narration is what's supposed to deliver the immersive effect).

## Approaches Considered

### Approach A: Minimal — raise the per-line character cap
Raise the LLM prompt's requested length from ~28 to ~40-50 chars/line (and `MAX_LINE` itself further if needed, e.g. to 60-70 — it's already 50 today, tuned as the validation ceiling, separate from the ~28-char prompt target). Smallest diff (two files: `llm.ts`, `runner.ts`). Risk: every turn gets slightly slower, box may wrap to more visual lines than before. Effect: modest — likely not enough to read as "more immersive."

### Approach B: Two-tier — short routine turns, long climax moments
Reuse the existing epilogue pattern (already ships 160 chars over 2-3 sentences on a 15s hold) for boss-hit/boss-kill events specifically, leaving routine correct/retry/flee turns untouched at 28 chars. Concentrates the "story" budget where it has the highest payoff (dramatic peaks) without taxing the repetitive early-game loop.

### Approach C: Multi-segment narration, per-segment cap unchanged (CHOSEN, user-proposed)
Don't touch the 28-char-per-segment limit at all. Instead widen the segment count every narration event can carry, from the current hard-coded max of 2 (`line` + `then`) to 3-4, played back in sequence via the `Sequence`/▼ component already built for this (currently only exercised with 2 segments). Total per-turn playback time grows (more segments × ~2.2s pause each), but no single line ever gets long enough to look cramped or wrap awkwardly — every individual beat stays punchy, matching the game's established tone. Directly reuses existing infrastructure (`Sequence`, `▼` continuation indicator, `LINE_PAUSE_MS`) rather than inventing a new mechanism.

## Recommended Approach

Approach C, per the user's explicit choice — reasoned, not just preferred: they want the shared/player experience to genuinely lengthen, not a host-only workaround, and per-segment length stays disciplined (matches the tone reviewers already tuned) while total narrative content grows.

## Open Questions

- **[RESOLVED — /plan-eng-review D2, corrected by D3] 3 segments for events with a next team; 2 segments for events without one.** `lib/narration/events.ts`'s `toNarrationEvent()` (line 30-33) already structurally omits `next` for `boss-kill` and any event ending the game ("A finished game has nobody next: the last line stands alone") — D2's original "fixed 3 for every event type" didn't account for this and would have needed to invent unrequested "transition" content for events that have no next team to transition to. D3 (Outside Voice finding, verified against the actual code) fixes this: has-next events get 3 segments (result + atmosphere/detail + transition), no-next events (boss-kill, the game's last judged event) get 2 (result + atmosphere, no transition) — this rides the existing `next`/no-`next` branch already in the code rather than inventing a new content type. Not event-type-dependent in the sense Approach B was (that assigned segment counts by event NAME); this assigns by an existing structural property (has-next-or-not) the code already branches on.
- **[RESOLVED — /plan-eng-review D1] Wire shape is a variable-length array, min 1 max 3 (target is 2 or 3 depending on has-next, per D3), not a fixed-size tuple.** The LLM won't reliably produce exactly the target count every call (see the reliability open question below) — every consumer (`Sequence` playback, `tts.ts`'s `shouldSpeakNarration` replay-detection) must correctly handle any length 1-3, not assume a fixed count. `shouldSpeakNarration`'s equality check needs to become an array comparison (length-sensitive, not just per-field), so it correctly detects "same eventId, different segment count" as a real content change, not just "same eventId, different text in slot 1/2." Rejected: fixed 4-slot with empty-string padding — `Sequence` would still play the empty segments unless separately filtered, which just relocates the variable-length problem into a "filter empty strings" problem instead of solving it.
- **Interruption behavior when a narration sequence is still playing and a new one arrives.** Pre-existing behavior (the `Sequence` component remounts on a new `eventId` key, cutting off whatever was still animating) — not introduced by this change, but more segments makes it more likely to actually happen in practice. Eng-review should decide whether this needs addressing now or can ship as a known limitation.
- **`lib/narration/tts.ts` ripple effect.** The TTS feature (shipped this session, v0.7.0.0) consumes the same `line`/`then` 2-slot shape via `SpokenNarration`. Widening to an array needs `shouldSpeakNarration`'s replay-detection logic re-verified against the new shape — this is exactly the kind of thing the TTS feature's own adversarial review caught bugs in last time (a correction to an already-replayed line being silently dropped), so treat this as a real risk area, not a mechanical find-and-replace.
- **LLM prompt reliability at 3-4 segments.** The model already doesn't reliably keep to length (`fitToLimit()` exists specifically to salvage over-length output) — reliably producing 3-4 *distinct, short* segments per call (rather than one run-on segment or dropping to 1) needs real testing against the live API before committing to the exact count.
- **What do segments 3-4 actually narrate?** The current 2-slot design already has a defined purpose for each slot (`line` = what just happened, `then` = who's up next). Segments beyond that have no authored content or prompt language yet, on either the LLM side (`llm.ts`'s `buildPrompt()`) or the scripted fallback side (`scripted.ts`'s hand-written variant pools) — this is new authoring work, not just widening a type. Eng-review needs a concrete answer (e.g., a scene-setting beat, an atmosphere line, more of the "what happened" story) before implementation starts.
- **Host live-edit (`HOST_EDIT_NARRATION`) at 3-4 segments.** Today it only ever edits `narration?.line` (the first segment) via `MoreDrawer`; the host UI has no notion of which segment a given client is currently displaying (that timing is client-side, in `Sequence`). Decide: edit only the currently-typing segment, edit all remaining segments, or redesign the feature.
- **`DEFAULT_HOLD_MS` re-tuning.** Currently 3000ms, tuned against 1-2 segment LLM latency. A 3-4 segment completion is a longer generation that plausibly needs a longer hold — otherwise more turns silently fall back to scripted lines, undermining the whole point of the change.

## Success Criteria

- A host running a real session reports the narration reads as more of a continuous story, not disconnected captions.
- Per-segment length stays within ~28 chars (the LLM prompt's requested target — the codebase's actual enforced ceiling, `MAX_LINE`, is 50; whether this feature introduces a stricter 28-char *enforced* cap for multi-segment lines, or keeps 28 as an aspirational prompt target only while still validating against 50, is an open implementation decision for eng-review, not settled by this doc).
- Total added playback time per turn is bounded. `Sequence` (`components/pixel.tsx`) only pauses *between* segments, not after the last one — k segments means k-1 pauses, not k. At 45ms/char typewriter + `LINE_PAUSE_MS = 2200` per gap, and ~28 chars/segment: today's 2-segment case runs ~4.7s (2×1.26s typing + 1×2.2s pause); the chosen 3-segment target (D2) runs ~8.2s (3×1.26s + 2×2.2s) — roughly +3.5s per turn, less than double today's time. Target: stay at or under ~8.5s per turn, pending real playtest confirmation that this doesn't feel sluggish — if the playtest says otherwise, this is the number to revisit (dropping segment count, not raising it).
- `lib/narration/tts.ts` (TTS feature) speaks every new segment correctly, with the same replay-safety guarantees as today — verified with tests, not assumed.
