## Problem Statement

一款架構類似 HITSTER! Online 的聚會派對遊戲：host 開網頁作為共享大螢幕，玩家用手機加入互動。玩家分隊探索地城，透過答對問答題擊敗怪物、獲得裝備，最終挑戰地城首領，依總分決定贏家。

## What Makes This Cool

不只是題目接題目的 quiz app，而是包在一個持續演化的地城冒險故事裡 —— AI 生成敘事、營造緊張感，讓玩家感覺自己真的在探索。差異化：比 Kahoot/Jackbox 多了持續演化的冒險故事線；比 AI Dungeon 多了多人即時派對協作與明確勝負規則。

## Constraints

- 已有 HITSTER! Online 的 host/player room 連線基礎設施可直接複用
- 沿用《Monster Eater: A Delicious in Dungeon Board Game》（改編自《迷宮飯》的桌遊）的分數/戰鬥判定概念，但只借用公式，不移植整套規則（**修正**：初版誤植為鈴木銀一郎 1983 年的《MONSTER MAKER》，經使用者更正）
- 10x 願景（角色養成、跨場次進度）明確排除在 MVP 之外

## Premises

1. 架構沿用 HITSTER! Online 的 host/player 連線模式。
2. **修正（/plan-eng-review Outside Voice 發現與原始 Premise 2 矛盾，已由使用者確認）**：核心迴圈是**全域回合制**——所有隊伍依序輪流答題，不論該隊當下在一般怪物房還是首領房；不是「各隊獨立推進、非同步答題」（此為初版用詞錯誤，已修正）。輪到某隊時系統依其當前所在房間出題。答對過關；答錯可選「逃跑」（換題/推進，放棄該房獎勵）或重答。每隻怪給分按難度權重，累積分數達門檻 X 才能挑戰首領。**已知代價**：N 隊時每隊只有 1/N 時間在答題，其餘時間等待其他隊伍——已決定加入緩解機制（見下方 Premise 3.5）。
3. **遊戲本質上是回合制**：所有隊伍依序輪流答題（不論該隊目前在一般怪物房還是已進首領房）。輪到某隊時，系統依據該隊目前所在的房間出題：在一般怪物房，答對過關；已進首領房，答對則對首領造成一次傷害並判定首領是否死亡——死亡則把首領擊殺獎勵給當前輪到的隊伍，未死亡則輪到下一隊答題。**因為是回合制，不存在多隊「同時」提交答案的即時並發問題**，不需要伺服器時間戳排序或樂觀鎖機制（修正自初版前提，見下方 Architecture Review）。先到首領房的隊伍先開始攻擊，後到的隊伍加入同一輪詢順序；只有讓首領血量歸零的那一輪答對的隊伍拿首領擊殺分，其餘參戰隊伍不拿尾刀分——但因為最終比的是總分，光靠一般怪物累積的分數仍有機會贏，不完全依賴尾刀。
4. AI 敘事**自己寫敘事狀態管理層**（追蹤各隊房間進度、首領戰況等結構化遊戲狀態），只把結構化狀態餵給 LLM API 生成旁白文字——不把敘事整個外包給現成的黑盒 DM agent（修正自初版前提，見下方 Cross-Model Perspective）。
5. Monster Eater 公式用於：(a) 怪物美術/強度對應表，(b) 戰鬥算分，例如擊敗首領拿 3 顆 D6 隨機分數。**已決定簡化**：不採用原版「難度與分數刻意不正相關」的風險/獎勵取捨設計，本作難度與分數直接正相關（1-5 分連續值）。
6. 角色養成與跨場次進度屬於 10x 願景，MVP 不做。
7. **新增（第一輪範圍內拉進來的緩解機制）**：全域回合制的等待時間風險（N 隊時每隊只有 1/N 時間在答題）用一個輕量旁觀機制緩解——等待中的隊伍可以在自己手機或共享畫面上看到目前輪到哪一隊、他們面對的題目/房間進度。這**不是**Approach B 完整的「共享大螢幕活地圖」（那還是留在第二輪，含美術/詳細戰況等），只是最小可行的「誰在答、答到哪」提示，第一輪範圍就要做。

**被推翻的方案：** 尾刀機制曾被 cross-model second opinion 挑戰為可能傷感情的設計（建議改成「基礎分+擊殺獎勵」），使用者評估後選擇保留尾刀機制原樣，理由是首領分是總分之外的加成，一般怪物的累積分數本身就足以讓隊伍有勝算，不需要為了公平而稀釋尾刀的競速刺激感。

## Cross-Model Perspective

獨立 Claude subagent 的冷讀分析（未看過本次對話，僅基於結構化摘要）：

- **沒想到的最酷版本**：主畫面變成即時「活地圖」，同步顯示所有隊伍進度，AI DM 插播其他隊伍戰況（"與此同時，紅隊正逼近王座…"），把各自獨立解謎變成有觀戰張力的競速——這比現有設計多不了多少工，卻能把 party game 的社交能量從「各自看手機」拉回「大家一起看大螢幕尖叫」。
- **關鍵興奮點**：「AI-generated narration, sound, tension, so players feel like they're really exploring」——顯示核心訴求是氛圍/沉浸感本身，而非計分系統。風險是容易在 MVP 階段超支打磨敘事，忽略最該優先驗證的 boss 並發機制。
- **現成工具能幫到哪**：HITSTER! Online 的 host/player room 連線可直接複用（第一個 50%）。但現成的 DM AI agent（AI Dungeon、Discord DM bot、SillyTavern）都是為單人/小群自由文字冒險設計，無法支援「多隊伍平行推進+明確勝負規則」，不能當黑盒子接入——這一點被採納，修正了原始前提 4。
- **原型建議**：一個週末先做「文字版 boss 戰 last-hit 機制」跟真人朋友測一輪，因為這是全案唯一沒有先例可抄、最可能翻車的社交設計；AI 旁白可以後補。
- **尾刀機制風險**：subagent 建議改成「基礎分+擊殺獎勵」以避免傷感情，使用者評估後選擇保留原設計（見上方 Premises 的「被推翻的方案」）。

## Approaches Considered

### Approach A: 最小可行版 (MVP)
直接復用 HITSTER infra，固定 5 房地城 + 文字題庫，旁白手寫固定文字 placeholder（不接 AI），簡單固定分數，先驗證整套玩法（含 boss 尾刀機制）好不好玩。Effort: S（human ~1 個週末）。Risk: Low。Reuses: HITSTER host/player room 連線全部。

### Approach B: 理想架構
在 A 的基礎上加上自寫敘事狀態管理層（結構化遊戲狀態餵給 LLM 生成旁白）、host 題庫編輯 UI、怪物難度對應表、共享大螢幕活地圖（即時看到各隊進度）。房間數不再像 A 一樣寫死 5 房，改成透過 host 題庫編輯 UI 可設定。Effort: L（human ~3-4 週）。Risk: Med。Reuses: HITSTER **連線/傳輸層**（WebSocket、room code、手機加入流程）——但每隊獨立非同步推進、首領房多隊並發、活地圖聚合廣播，都是 HITSTER 原本同步單軌問答架構沒有的新狀態管理，屬於淨新增，不是直接沿用。

### Approach C: 先驗證最風險的部分（實驗式，未選）
不建地城，只做獨立的「boss 多隊並發答題+尾刀判定」小體驗，先把最沒先例可拆的機制單獨測。Effort: XS。Risk: Low。未選用，理由：使用者想要一次到位的完整體驗。

**採納但未整體改變方案選擇的建議：** Cross-Model 第二意見建議先用 Approach C 的做法單獨測 boss 機制。使用者維持選擇 Approach B 的完整體驗，但此建議被部分採納——Next Steps 加入了一個「boss 機制先跟真人測過，再投入敘事層/UI/活地圖」的中途檢查點（見下方 Next Steps 第 4 步），而不是把整個第一輪建置延到最後才給人玩。

## Recommended Approach

**Approach B（理想架構）**——使用者選擇。核心理由：敘事狀態管理層是長期要持續擴充的基礎，現在建立可避免之後重寫；共享大螢幕活地圖是 cross-model 第二意見指出的「最酷版本」關鍵，值得在第一輪就做出來而非事後補。**風險緩解：** 為避免 Cross-Model 指出的「在最高風險的 boss 並發機制被驗證之前，先把工投入敘事/UI/地圖」這個陷阱，Next Steps 把 boss 邏輯與一次輕量真人測試排在敘事層/host UI/活地圖之前（見下方）。

## Open Questions

**會擋住開發、須優先解決：**
- ~~逃跑後「換題」的重擲單位~~ **已決定**：逃跑後換一隻新怪物（不是同一隻怪物換題），但新怪物的難度會降級（給比較簡單的怪物跟題目）——等於是有代價的保底機制：逃跑放棄了原本較高難度/分數的機會，換取一個較容易過關的選項。題庫如何避免同場重複抽到同一題仍待定義（次要，非阻塞）。
- ~~房間題目的難度分級標準~~ **已決定**：難度與分數正相關，1-5 分連續值（不採 Monster Eater: A Delicious in Dungeon Board Game 式的「難度/分數風險取捨」——該遊戲難度與分數刻意不正相關，本作決定簡化為純正相關）。Host 出題時直接給每題一個 1-5 的難度分數。
- ~~進首領房的門檻分數 X~~ **已決定**：固定值（第一輪範圍暫定 15 分，實作時可依真人測試手感微調），不依隊數/房間數動態調整。
- ~~回合輪詢順序如何決定~~ **已決定（/plan-eng-review Outside Voice + 使用者確認）**：固定順序（隊 A→B→C→...循環），不依到達首領房的先後排——避免「打得快的隊伍系統性累積先手優勢、強者愈強」的滾雪球問題（Outside Voice 指出的風險）。仍保留一個小優勢：固定順序下第一個被排到的隊伍永遠最先輪到，第 4 步輕量真人測試須驗證這個小優勢是否明顯。

**其他待釐清：**
- 敘事狀態管理層要用什麼 LLM API（成本、延遲、可靠度）尚未選定；也尚未定義**旁白延遲目標**，以及 LLM 生成「太慢」與「直接失敗（逾時以外，如額度用盡、伺服器例外）」這兩種情況是否共用同一套 fallback 文字策略，或需要分開處理。
- ~~平手（總分相同）時的決勝規則~~ **已決定**：並列第一名，不額外比賽。
- 若某隊遲遲無法累積到門檻分數、永遠進不了首領房，遊戲該如何結束（時間上限？強制推進？）尚未定義。
- 支援的隊伍數/每隊人數上下限尚未定義——這會影響首領房並發設計與活地圖版面。
- 玩家如何加入特定隊伍、是否需要輸入暱稱、host 如何分隊，尚未定義。
- 是否支援多場次並行（多組 host 同時各開一場），還是單場次全域狀態，尚未定義。
- ~~斷線重連策略~~ **已決定（/plan-eng-review）**：第一輪範圍純 in-memory，不持久化。伺服器重啟則整場遊戲重來；玩家手機斷線/host 分頁重整靠重新連上同一個 room code 恢復畫面（連線層邏輯，非遊戲狀態持久化）。正式上線前需重新評估。
- 活地圖具體要顯示哪些內容（各隊房間位置？分數？首領血量？）尚未列清單，目前只有「即時看到各隊進度」這種籠統描述。
- Host 自訂題庫的文字內容進入 LLM 旁白 prompt 前，尚未定義基本的內容過濾/防注入處理。

## Success Criteria

**輕量真人測試成功標準（適用於 Next Steps 第 4 步）：**
- 多隊真人跑完整套核心流程：進地城 → 過怪物房 → 累積分數達門檻 → 進首領房 → 尾刀判定 → 依總分決定贏家。
- 玩家對回合輪詢順序與尾刀判定的公平性沒有明顯負面觀感。

**已完成（2026-09-18）**：用 [docs/question-bank-2026-taiwan.md](../question-bank-2026-taiwan.md) 的真實題目跑了一場真人測試。結果：**機制本身沒有引起抱怨**（回合輪詢順序、尾刀判定、步調都沒被玩家講出問題），達成上述成功標準。但玩家明確回饋：**光靠機制骨架無法判斷這遊戲好不好玩**——這款遊戲的核心賣點取決於 DM 敘事沉浸感、遊戲畫面、操作介面，沒有這些玩家沒辦法評價「好玩」。這印證了 Cross-Model Perspective 當初的判斷（見上方，「核心訴求是氛圍/沉浸感本身，而非計分系統」）——機制驗證過關，真正的好玩與否要等第二輪的敘事層/UI/活地圖做出來才能評估。

**完整版真人測試成功標準（適用於 Next Steps 第 9 步）：**
- Host 可以透過 UI 自訂題庫與答案，不需要碰程式碼。
- 共享大螢幕活地圖即時反映所有隊伍進度（至少涵蓋：各隊目前所在房間、目前總分、首領房戰況——實際清單待 Open Questions 的活地圖項目定案後補齊）。
- AI DM 旁白根據結構化遊戲狀態生成；驗收方式為抽樣 N 則旁白對照當下真實遊戲狀態，人工檢查是否有事實矛盾（而非承諾「不出現」幻覺——LLM 生成內容無法保證零錯誤，只能盡量壓低並可檢驗）。

## Distribution Plan

Web service，比照 HITSTER! Online 現有的部署管線（沿用既有 host 網頁 + 玩家手機瀏覽器加入的架構，不需要額外的安裝或分發管道）。

## Next Steps

1. ~~確認 runtime~~ **已確認（2026-09-17）**：複用 HITSTER! Online 的技術棧——**Next.js 16.2.4**（React 19.2.4）+ **PartyKit**（`partykit`/`partysocket`，host/player room 連線層，位於 `party/index.ts`）+ Tailwind CSS 4 + TypeScript 5。測試：**Vitest**（單元）+ Testing Library + **Playwright**（E2E）。建立新專案骨架，複用 PartyKit 連線/傳輸層；同時規劃新增的每隊獨立狀態機、首領回合制、旁觀提示廣播這幾塊新架構（獨立的 party room handler，不是修改 HITSTER 本體，是同樣技術棧的新專案）。
2. ~~前置定義~~ **已全部定案**（逃跑重擲單位=換怪物+降級難度、難度權重=1-5分正相關、門檻分數X=固定15分、總分公式=單純相加）——見上方 Premises/Open Questions 的決議記錄。可以直接設計並實作房間/怪物狀態機（房間序列、答對過關、答錯逃跑降級、分數累積、門檻判定）。
3. **前置定義（擋住本步驟，須先決定）**：回合輪詢順序怎麼決定（固定/隨機/依到達順序）。定案後實作首領房的回合制答題與尾刀判定邏輯——遊戲本質是回合制，不需要即時並發鎖定機制（見上方 Premise 3 的架構修正）。
4. **輕量真人測試檢查點**：用手寫固定文字或最簡陋的介面，找朋友先把「房間推進 + boss 回合制攻擊 + 尾刀判定 + 總分決勝」這條主線玩過一輪，驗證核心玩法好不好玩、以及玩家對輪詢順序與尾刀判定的公平性觀感——在投入敘事層/host UI/活地圖之前先確認這條最高風險的主線是好玩且公平的。
5. 設計敘事狀態管理層的資料結構（各隊進度、首領戰況），先用假資料/固定文字驗證資料流。
6. 接入 LLM API，把結構化狀態轉換成 DM 旁白 prompt，並實作延遲 fallback（旁白生成中先顯示佔位文字/固定過場句）。
7. 建立 host 題庫編輯 UI 與怪物難度/美術對應表（Monster Eater 公式，1-5 分正相關）——先確認這是不是第一輪真人測試就需要的東西，或可以先用設定檔/JSON 頂著，UI 留到驗證完玩法後再做。
8. 建立共享大螢幕活地圖，即時顯示各隊進度（內容清單見 Open Questions）。
9. 找朋友進行完整版真人測試（含敘事、UI、活地圖），對照第 4 步的輕量測試結果檢視體驗提升是否符合預期。

## Reviewer Concerns

三輪對抗式審查後仍未解決、留給實作階段處理的問題（品質分數穩定在 7/10，未再改善，故不繼續迭代）：

1. ~~總分組成公式未給出~~ **已決定**：單純相加 —— 總分 = 一般怪物累積分（含逃跑降級後的怪物分數） + 首領尾刀加分（首領死亡時的 3 顆 D6 隨機分數，見 Premise 5）。無額外權重或倍率。

## Failure modes

| Codepath | 可能的生產環境失敗方式 | 測試涵蓋？ | 錯誤處理？ | 使用者體驗 |
|---|---|---|---|---|
| `answerQuestion()` 答對判定 | 題目 ID 對不上當前隊伍房間狀態（前端快取過期） | [GAP] 無 | [GAP] 無 | 若無防護，可能靜默算錯分——**建議標記為 critical gap** |
| `nextTurn()` 輪詢推進 | 佇列中某隊已離線/斷線，輪到時卡住整場遊戲（全域回合制下影響所有人） | [GAP] 無 | [GAP] 無 | 全場卡住、無提示——**critical gap**，全域回合制放大了單隊離線的影響範圍 |
| `bossEncounter()` 尾刀判定 | 首領血量計算的加減法邊界（剛好扣到 0 以下） | [GAP] 無 | [GAP] 無 | 若無測試，可能誤判尾刀歸屬——直接影響使用者最在意的公平性 |
| 伺服器重啟 | 進程異常終止 | N/A（已知限制） | 無（已決定不做） | 整場遊戲遺失，需要清楚的提示畫面告知玩家重開 |

**Critical gaps（無測試 + 無錯誤處理 + 會靜默失敗）**：`answerQuestion()` 的題目/房間狀態校驗、`nextTurn()` 的離線隊伍處理，這兩項應在 Next Steps 第 2-3 步實作時就寫測試與錯誤處理，不要留到之後。

## Worktree parallelization strategy

Sequential implementation, no parallelization opportunity——Next Steps 第 1-4 步（連線層骨架 → 狀態機 → 首領回合制 → 真人測試）全部觸及同一個核心遊戲狀態模組，且彼此有明確依賴順序（狀態機需要連線層骨架、首領邏輯需要狀態機、測試需要兩者都完成），不建議拆多個 worktree 平行開發。
